# DSH Livery 0.2.2 — wallpaper studio and plugin-detail surface

Status: **implementation design note for the `0.2.2` target release**. Baseline:
published `dsh-livery@0.2.1`. This is freeze v3: v2 closed the five original
blockers; v3 closes the precision review of stale boot CSS, persistence
identity/provenance, cross-tab sidecar races, detail wiring/data sources,
slot-claim boundaries, image-host matching, copy states and packaging surfaces.
The client-only implementation described here is present in the working tree;
0.2.2 acceptance/evidence has **not** been run yet, and the package is not
published.

Before packaging, this file must either be updated to describe the accepted
shipped behaviour or move to `docs/archive/`; a tarball must not ship a plan
labelled “pending”. The current detail/slot design is split into
[`plugin-detail-surface.md`](plugin-detail-surface.md); the unscheduled Host
update-API proposal moved to the repository path
`docs/archive/host-update-preflight-proposal.md` (not shipped).

## 1. Release goal

`0.2.2` is a **client-only feature release**:

1. Refactor the wallpaper studio: 8 visible curated built-ins, a separate
   `kind: 'style'` background, a keyless provider registry with real
   attribution, and explicit request/failure states.
2. Add a truthful Livery plugin-detail surface: use the three `plugins.detail.*`
   client slots that both the 0.2.1 and 0.2.2 plugin-manager client already
   declare (verified in the shipped packages), and fix the client handshake so a
   real 0.2.1 → 0.2.2 bundle update survives a hot client replacement on Web.

It does **not** add keyed providers, a Host fetch proxy, secret storage, a
pre-update Host API, or an update button of its own.

## 2. Frozen decisions

- **Exactly 8 visible built-ins**, chosen from the existing 24 IDs (no new
  designs): `paper`, `ink`, `aurora`, `cyber`, `dusk`, `minimal`, `mono`, `sand`
  — that order. The other 16 remain loadable as **Classic** with byte-identical
  IDs and CSS. No ID is remapped.
- **`kind: 'style'`** is a fourth persisted selection kind, stored in a sidecar
  localStorage key so a 0.2.1 client can never overwrite it (see §4.3). It is not
  a reserved built-in ID.
- **Preset schema v2** adds `wallpaper.kind: 'style'` and attribution URLs; v1
  stays importable. 0.2.1 rejects v2 files with its existing
  `schema-version` error; that downgrade limitation is documented.
- **Five keyless provider targets**, each gated before code: Openverse,
  Wikimedia Commons, NASA Image Library, The Met Open Access, Art Institute of
  Chicago. The committed gate record
  (`docs/research/provider-access-gate.json`, reviewed 2026-11-23) accepts
  **Openverse and Wikimedia Commons only**: NASA is rejected (unverifiable
  rights and inconsistent image-CDN CORS), Met and AIC are deferred (image-CDN
  CORS absent / verification blocked), and Picsum is rejected (Unsplash licence
  prohibits this use). 0.2.2 therefore lists exactly those two providers; an
  existing remote selection from a removed provider still hydrates as a cached
  remote image. The release ships fewer providers rather than adding a keyed
  source to compensate.
- **No Pexels, Pixabay, or Unsplash** in 0.2.2; no Bing daily wallpaper; no DSH
  `web_fetch` dependency; no Host proxy route; no API keys or secret storage.
- **No Host preflight update API**, no fake disabled Update button, no
  interception of the Host's own controls. The update-boundary copy is neutral
  and capability-free (no host-version-string branching).
- **HMR:** accept one exact previous plugin build (`0.2.1`) as a `stale` boot
  payload, refetch the catalog and re-adopt config; keep fail-closed for anything
  else. The hot-update claim is **Web-profile only**; Desktop requires a
  renderer reload after an update (see §5.3).
- **Panel control surface:** two background-preset cards (`No wallpaper`,
  `Follow style`) above the unchanged four image-source tabs; a native
  `<select>` for providers inside Online. Details in §4.1.
- **Budgets:** client gzip **72 KiB (73,728 B)** approved; the tarball cap stays
  **4 MiB (4,194,304 B)**. 0.2.2 assets are compressed/sized to fit without
  visible degradation (see §6); do not raise the tarball cap.
- **Acceptance:** all 13 scopes re-accepted on one final tarball (fresh install),
  plus update-probe runs on Web that install the exact published 0.2.1 tarball,
  update through the running Host's plugin-manager install dialog to the exact
  candidate tarball, and record the transition: required on one `0.2.2`-line
  Web scope, and on one `0.2.1`-line Web scope when that line's plugin-manager
  install dialog proves it can install over the tarball-installed bundle (§5.4).

## 4. Workstream A — wallpaper studio

### 4.1 UI hierarchy and request behaviour

```text
Current wallpaper / effects            (unchanged hero card)

Choose a wallpaper
  Background presets
    [ No wallpaper ]   [ Follow style ]     ← two cards, real buttons
  Or choose an image                        ← unchanged four source tabs
    Online | Built-in | Recent | Local & link
```

- The two preset cards are single-select (`aria-pressed`): `No wallpaper` is
  selected when the selection is `undefined`; `Follow style` when
  `selection.kind === 'style'`. `Follow style` is disabled with a visible,
  described reason when no catalog/tokens are available.
- `SOURCE_TABS` stays exactly four and remains the **only image-source picker**.
  The workbench invariant is updated to: “the two background-preset cards plus
  the four image-source tabs are the only source-picker surfaces; no other
  control changes the wallpaper.”
- The hero’s existing Clear button stays as a shortcut for `No wallpaper`.
- Online tab: a native `<select id="wallpaper-provider">` labelled “Source” with
  `Auto` first, then the gate-passed providers in registry order (0.2.2 ships
  Openverse and Wikimedia Commons). Changing the provider clears results to
  `idle` and never fetches implicitly. Native keyboard behaviour is the keyboard
  model; no custom listbox.
- **No request on panel mount or app boot.** The default image tab is
  `builtin`, so opening the Wallpaper page renders the 8 curated swatches without
  network. The first activation of the Online tab triggers exactly one batch for
  the current provider/query (guard: only when status is `idle`). Later tab
  switches do not refetch. Search, Random, Refresh and Retry are the only other
  request triggers.
- Online state union: `idle | loading | ready | empty | timeout | rate-limited |
  auth-required | unavailable | invalid-response`. `empty` is a settled state,
  not a failure. `auth-required` is kept for completeness (401/403) even though
  keyless providers should not need it.
- **Auto failover:** one overall deadline of 12 s from request start; each
  attempt gets `min(6 s, remaining)`; Auto tries at most two gate-passed
  providers in registry order and names the provider that served the results
  (`Served by: …`, polite live region). A pinned provider makes one attempt and
  never silently changes. All failures produce one error with Retry and links
  to Built-in/None. Picsum is never selected by Auto.
- No background health check, no prefetch, no polling, no telemetry.
- Provider thumbnails are loaded only for returned results, as today.

### 4.3 `kind: 'style'` and sidecar storage

`kind: 'style'` must survive a 0.2.1 downgrade. Adding it to the main selection
record cannot satisfy that: 0.2.1 rejects an unknown kind (and any raised
`schemaVersion`) as an invalid record and rewrites the whole record on its next
effects/selection change. The frozen design is a **sidecar key**:

```ts
// unchanged main record (0.2.1-compatible bytes)
WALLPAPER_STORAGE_KEY = 'dsh-livery.wallpaper.v1'   // historical name, keep
WALLPAPER_STATE_SCHEMA_VERSION = 2                  // unchanged

// new sidecar, unknown to 0.2.1
WALLPAPER_STYLE_STORAGE_KEY = 'dsh-livery.wallpaper.style.v1'
WALLPAPER_STYLE_SCHEMA_VERSION = 1

type StyleWallpaperVariant = 'mesh'
interface StoredWallpaperStyle {
  readonly schemaVersion: 1
  readonly variant: StyleWallpaperVariant
  /** Identity of the main-record write this style belongs to. */
  readonly revision: number
  readonly sourceId: string
}

type WallpaperSelection =
  | { kind: 'builtin'; id: BuiltinWallpaperId }
  | { kind: 'remote'; url: string; provenance?: WallpaperProvenance }
  | { kind: 'upload'; key: string }
  | { kind: 'style'; variant: StyleWallpaperVariant }
  | undefined
// StoredWallpaperSelection keeps the 0.2.1 kinds and adds one additive optional
// `provenance` member on `remote`. 0.2.1 parses the remote URL normally (unknown
// members are ignored) and drops provenance on its next state write.
// style is never written into the main record.
```

Hydration is `style` **iff** the sidecar parses, the main record parses with
`selection` cleared (`undefined`/`{kind:'none'}`), **and the sidecar’s
`(revision, sourceId)` exactly equals the main record’s identity**; otherwise the
main record wins and a stale sidecar is ignored. This is the same
`(revision, sourceId)` ordering the controller already uses between tabs, so a
late style write from a behind tab cannot resurrect style over a newer clear or
image. The same identity check applies when a tab adopts an external main record:
it re-reads the sidecar after adoption rather than keeping its own remembered
style state.

Persist ordering, with mocked-storage and conflicting-tab tests:

1. to style, or any persist while style is selected: write the main tombstone
   with its new `(revision, sourceId)` **then** write/refresh the sidecar with
   the same identity. A sidecar-write failure leaves “no wallpaper”, never a
   half-style.
2. to image: write the main selection **then** remove the sidecar.
3. to none: remove the sidecar **then** write the main tombstone (the only order
   that cannot resurrect style through a stale sidecar).

The main record remains the only ordering signal; a sidecar-key event is
re-resolved **only** under the identity this tab already adopted from the main
record, and every main-record persist while style is active refreshes the
sidecar identity. **Write guard:** before writing or
refreshing the sidecar, re-read the current main record; write only when its
identity still equals the writer’s identity. If another tab’s newer state won
meanwhile, skip the sidecar write entirely and leave the winner’s sidecar
untouched — the normal storage-event adoption re-syncs this tab. The identity
check at hydration prevents a stale sidecar from being adopted; this write guard
prevents a behind tab from overwriting the winner’s sidecar in the first place
(and therefore from making the active style disappear). The existing “Clear
local data” action keeps its semantics — it clears cached images/history/unused
uploads and preserves the current wallpaper — so it must preserve **both** the
main record and the style sidecar, not delete either key. The hero Clear /
selecting `No wallpaper` is what removes the sidecar through the none-path
ordering.

Documented residual downgrade behaviour:

| 0.2.1 action after 0.2.2 chose Style | 0.2.2 result after re-upgrade |
|---|---|
| reads only / makes no wallpaper-state write | Style preserved (identity still matches) |
| changes effects, position, image or clears | Main identity moves on; Style is not shown; sidecar bytes are retained but stale and are ignored (and cleaned up on the next 0.2.2 style/image/none write) |
| rewrites a remote selection | Image displays; its provenance URLs are dropped by the 0.2.1 writer (0.2.1 has no such fields) |

The downgrade is therefore data-preserving but not state-preserving: 0.2.1 never
deletes the sidecar, and 0.2.2 never lets a stale sidecar override a newer main
record.

Style generation: one pure function over the catalog tokens, one fixed recipe,
per mode (light/dark) from the same `TokenMap` the wallpaper builder already
receives; deterministic and byte-identical for the same tokens:

```text
radial-gradient(120% 140% at 12% 0%,
  color-mix(in srgb, var(--dsw-alias-brand-primary) 24%, transparent) 0%, transparent 55%),
radial-gradient(110% 130% at 88% 18%,
  color-mix(in srgb, var(--dsw-alias-bg-layer-3) 18%, transparent) 0%, transparent 60%),
linear-gradient(160deg, var(--dsw-alias-bg-base) 0%, var(--dsw-alias-bg-layer-2) 100%)
```

- Token names are already present in `src/generated/stock.ts`. Mix percentages
  are global constants; if a contrast audit fails, adjust the constants, never
  add per-style overrides.
- No `url(...)`, blob, IndexedDB row or cache record is created. The layer is
  emitted per light/dark like today’s wallpaper rules; the atmosphere layer uses
  the same mode-specific image.
- `canReposition` becomes `kind === 'remote' || kind === 'upload'`; style always
  returns `center`. The hero preview uses the mode-specific style image
  (`getRenderImage(mode)`), not a URL.
- No catalog/tokens: the style card is disabled with a visible reason, the
  controller rejects `setStyle` without tokens, and any already-persisted style
  selection hydrates as “no wallpaper” rather than painting an empty layer.
- Preset apply carries `{kind:'style', variant}` through the same sidecar write
  path (`PresetWallpaperTarget.selection` includes style); apply success compares
  kind+variant, and a style target is exportable only as preset v2.
- Contrast audit: for all 28 liveries × light/dark, composite each recipe stop
  over its base and require `--dsw-alias-label-primary` ≥ 4.5:1; plus
  determinism, light≠dark, no-cache, no-`url(`, and no-token fallback tests.

### 4.4 Provider registry

Replace the two ad-hoc parsers with a typed registry:

```ts
type ProviderFailure =
  | 'timeout' | 'rate-limited' | 'auth-required'
  | 'unavailable' | 'invalid-response'

interface WallpaperProvider {
  readonly id: string
  readonly label: LocalizedText
  readonly auth: 'keyless'
  readonly capabilities: { readonly search: boolean; readonly random: boolean }
  /**
   * Host allowlist for returned image URLs. Each entry is either an exact
   * hostname (`images.example.org`) or a wildcard subdomain (`*.example.org`,
   * matching any `x.example.org` and not `example.org`). Plain suffix matching
   * is forbidden.
   */
  readonly imageHosts: readonly string[]
  /** Same exact/wildcard rules for allowlisted redirect targets. */
  readonly redirectHosts?: readonly string[]
  fetchPage(request: {
    readonly query?: string
    readonly cursor?: string
    readonly pageSize: number
    readonly signal: AbortSignal
  }): Promise<
    | { readonly results: readonly WallpaperResult[]; readonly nextCursor?: string }
    | { readonly failure: ProviderFailure; readonly retryAfterMs?: number }
  >
}

interface WallpaperResult {
  readonly providerId: string
  readonly id: string
  readonly title: string
  readonly creator?: string
  readonly creatorUrl?: string
  /** `null` means: not selectable (no usable licence/attribution). */
  readonly license: { readonly name: string; readonly url?: string } | null
  readonly sourceUrl: string
  readonly fullUrl: string
  readonly thumbUrl: string
  readonly width?: number
  readonly height?: number
}
```

Rules:

- Every image URL is https, passes the existing public-host rules, and its
  hostname matches an `imageHosts` entry with the exact/wildcard rule above
  (`notexample.com` and `example.com.evil` never match `example.com`). Image
  downloads use `redirect: 'error'` unless the provider declares
  `redirectHosts`; a followed redirect’s final URL must still be https, public
  and match a declared redirect host. This replaces the Picsum-only redirect
  branch in `cache.ts` with a provider-declared policy; a provider without a
  usable allowlist ships no images rather than opening arbitrary hosts. Add
  negative tests for all three shapes (exact, wildcard, look-alike/eTLD
  suffix).
- `license: null` results are rendered but not selectable.
- Cursor is opaque and encoded per provider; page/offset/continue tokens are the
  provider’s business.
- 401/403 → `auth-required`; 429 → `rate-limited` with `Retry-After` when
  present, clamped to at most 60 s so one source's 24 h header cannot disable the
  whole Online tab; timeout → `timeout`; JSON/schema failure →
  `invalid-response`; DNS or network failure → `unavailable`.
- Online/Recent download failures show a stable-id `role="alert"` notice instead
  of being silently dropped. Recent history persists `providerId` through the
  write/merge path so the Openverse notice survives re-application.
- Cache key stays the URL hash. Provenance lives on the selection record, never
  in the cache key, so 0.2.1 caches still hydrate and the same URL stays the same
  image.
- `license` must be a real licence name; its URL is required whenever the
  licence requires an attribution link (CC BY/CC BY-SA), so a result missing a
  required licence URL is non-selectable. A provider brand is never a licence.
  Picsum is rejected by the gate and is not listed or passed to Auto; existing
  Picsum remote selections still hydrate as cached remote images through the
  legacy cache path, and no new result ever carries `license: 'Picsum'`.
- Capability-gated actions: Search is enabled only for providers declaring
  `search`, Random only for `random`. A pinned provider that lacks the
  capability shows the action disabled with a reason; Auto picks the first
  gate-passed provider that declares it, or disables the action when none does.

### 4.6 Attribution, recent history and preset v2

One authoritative store: the persisted remote selection carries optional
provenance; history is a display mirror.

```ts
interface WallpaperProvenance {
  readonly providerId?: string
  readonly title?: string
  readonly creator?: string
  readonly creatorUrl?: string
  readonly license?: string          // human-readable name, not a brand
  readonly licenseUrl?: string
  readonly source?: string
  readonly sourceUrl?: string
}
```

- `StoredWallpaperSelection.remote` gains an optional `provenance` member;
  `WallpaperSelection.remote` carries it in controller state;
  `parseStoredSelection` **parses** it and `toStoredSelection` **preserves** it
  (today the writer rebuilds a compact selection, which is what would discard
  metadata). 0.2.1 parses the remote URL normally, ignores the unknown member and
  keeps rendering the image; its next state write drops provenance, as recorded
  in the downgrade table in §4.3.
- `RecentWallpaperEntry` gains optional `creatorUrl`, `licenseUrl`, `sourceUrl`
  (old entries stay valid) and remains a mirror. The current image’s credit is
  resolved from the selection, so clearing history no longer removes the credit
  of the applied image. The legacy `ATTRIBUTION_STORAGE_KEY` is migrated once
  when its `identity === 'remote:<url>'`, then removed; the panel no longer owns
  a second attribution store.
- All provenance URLs are https, public-host, ≤2048 chars, and are rendered as
  `<a rel="noreferrer noopener" target="_blank">`; plain text is not enough for
  CC BY/CC BY-SA. Invalid URLs are dropped on write and rejected on preset
  import.
- Preset v2 attribution extends the v1 text fields with `creatorUrl`,
  `licenseUrl`, `sourceUrl` under the same validation; export drops invalid
  URLs, import fails with `attribution` and a `detail` field.
- Preset import accepts `schemaVersion: 1 | 2`. A v1 file keeps the
  `builtin | remote | null` wallpaper union (a v1 file claiming
  `kind: 'style'` is rejected as `wallpaper-kind` so both clients agree); v2
  adds `{kind:'style', variant:'mesh'}` with exact keys and a
  `wallpaper-variant` problem code. Export always writes v2.

### 5.2 Detail content

The section is a `<section>` with a heading and a `<dl>`; it renders only
observable facts:

- build version (`LIVERY_VERSION`), boot handshake state
  (`valid | stale | absent | mismatch`) and reason;
- installed package version from `subject.pkg.version` when present;
- host version, adapter id, short contract hash, catalog profile;
- catalog phase and applied CSS hash from `body[data-dsh-livery-hash]`;
- active style (`confirmedId`/`effectiveId`/`invalidSkinId`), active wallpaper
  kind/name from `getWallpaperController()?.getSnapshot().selection` (the runtime
  snapshot does not carry wallpaper state);
- update-boundary copy.

Copy is selected by handshake state; exactly one message is shown, never all
three:

| State | Copy |
| --- | --- |
| `valid` / no update in flight | “DSH’s plugin manager installs and updates Livery. If an update is installed, reload this page so the browser loads the new Livery client.” |
| `stale` | “Updated without a page reload; the startup frame came from the previous build.” |
| `stale` + catalog unavailable (degraded) | “The Livery client updated, but its catalog is unavailable; Retry or reload this page.” |
| `mismatch` / `reloadRequired` | “Reload required: this page still runs the previous Livery startup frame.” |
| `absent` | “Livery is not active on this host; the plugin manager still owns installation and updates.” |

No host version string is used to choose any of these; the state comes from the
handshake. Never claim Hot update / Restart required from a Host plan that does
not exist.

Acceptance: on every fresh-install **Web** scope the probe opens Plugins → Livery
and asserts the section/badge render, the actions are present, the row/item/
other-bundle subjects render nothing, and no Livery config-body slot is
registered. The Desktop probe does not run this check yet, so the
`0.2.1-rc.3` Desktop static-proof gap remains a documented per-scope limitation
until it does. If a host does not expose the plugin-manager page, record that
scope limitation explicitly instead of skipping silently. If the page exists but
the host lacks a declared detail slot, record the per-host declaration gap and a
skipped-with-reason detail check in the report/evidence; state the limitation in
`docs/verification.md` and the support matrix notes. That is a documented
detail-surface limitation for that host, not a release blocker, and it can never
be reported as a pass.

### 5.3 HMR handshake fix

`checkBoot` currently fails closed on **any** plugin-version difference, which
makes `runtime.ts`’s `hotReloaded` retry branch and `bootIdentity`’s stale-profile
branch unreachable. The frozen fix:

```ts
type BootCheck =
  | { kind: 'valid'; ... }                 // payload version === LIVERY_VERSION
  | { kind: 'stale'; staleFrom: string; ... } // exact allowlisted previous build
  | { kind: 'absent'; ... }
  | { kind: 'mismatch'; ... }

const STALE_BOOT_VERSIONS: readonly string[] = Object.freeze(['0.2.1'])
```

- Acceptance order: shape → certified `(hostVersion, adapterId, contractHash)`
  triple → `entryId` → version (`=== LIVERY_VERSION` → `valid`; exact membership
  in `STALE_BOOT_VERSIONS` → `stale`; anything else → `mismatch`) →
  `catalogProfile === adapter.catalogProfile` (strict; no “profile changed by
  HMR” exception) → `accepted` (`false` → `absent`).
- Exact string equality only; no semver, prefix or range inference. Extending the
  list is a reviewed release change tied to an accepted transition.
- Trusted stale fields: `hostVersion`, `adapterId`, `contractHash` (certified
  triple), `catalogProfile` (must equal the adapter’s), `entryId`,
  `pluginVersion` (allowlist membership). Diagnostic-only hints, never used to
  choose or paint CSS or as a config fallback: `skinId`, `cssHash`,
  `diagnostics`, `profileKind`. Never trusted: `catalogUrl` (the client fetches
  the build constant `/livery/api/catalog`), `bootStyleId`.
- `bootIdentity` always returns the certified adapter triple/profile; delete the
  dead profile branch.
- Runtime decision, frozen:
  - **Stale never adopts boot CSS.** `tryAdoptBoot` stays `valid`-only; the
    stale path always applies one catalog-derived `applyConfirmed` after the
    refetch.
  - `maybeSettle`/config fallback never uses a stale payload’s `skinId`: if the
    host config form is unavailable, stale falls back to `STOCK_ID`, not to the
    old boot skin.
  - On catalog success: ready, `bootStatus: 'stale'`, one `applyConfirmed`, the
    saved wallpaper/config re-applied.
  - On catalog failure after the 8 retries: fail closed to `degraded` with
    `presenter.removeBootArtifacts()`, `effectiveId: STOCK_ID` and the note
    “hot update detected; catalog unavailable — Retry or reload”. Do not keep
    the stale startup CSS and do not show the stale skin as active;
    `retryCatalog()` may recover to ready/stale without a page reload.
- On the stale retry path, treat a successfully fetched catalog whose
  `compilerVersion !== LIVERY_VERSION` as a transient failure (keep retrying,
  then fail closed); a 0.2.1-compiled catalog is never applied by a 0.2.2
  renderer. The update probe asserts the captured catalog's compilerVersion is
  the candidate version.
- Widen `BootPayload.pluginVersion` and `LiveryCatalog.compilerVersion` to
  `string`; add `stale` to `BootStatus` and every UI/diagnostic union. Keep
  `BootCheck.reloadRequired` (it already exists) and consume it in the detail
  section’s mismatch copy; do not leave it as a dead field. No auto reload.
- Tests: allowlisted `0.2.1` → `stale` with adapter and reasons; `9.9.9`,
  `0.2.10`, `0.2.0` → `mismatch`; profile/entry mismatch → `mismatch`;
  `accepted:false` → `absent`; frozen allowlist; `bootIdentity(stale)` uses the
  certified profile. Runtime: stale + catalog → ready in one fetch,
  `bootStatus: 'stale'`, exactly one `applyConfirmed`, zero `adoptBootStyle`;
  stale + config unavailable → stock fallback, never `payload.skinId`; stale +
  catalog permanently down → degraded/stock with boot artifacts removed, zero
  adopt/apply, then `retryCatalog()` recovers; transient catalog failure → retry
  then ready. Replace the two existing tests that assert fail-closed on an older
  payload.
- **Claim boundary:** DSH client HMR is a Web-profile mechanism (client-hmr SSE
  is Web-only; Electron does not use that path). The 0.2.2 hot-update claim is
  Web only. On Desktop, an update requires a renderer reload/app restart; the
  detail copy says so and no hot claim is made there.
