# DSH Livery 0.2.0 proposal — capability-aware GUI style engine

> **Status: proposal, not implemented and not released.** This note defines the
> intended 0.2.0 direction. It does not change the 0.1.9 manifest, host contract,
> catalog, published evidence or supported-host claims. A proposal is not an
> acceptance claim; each capability needs a frozen contract, implementation,
> tests and host evidence before it ships.

## 摘要（中文）

- 0.2.0 定位是**能力感知、可安全降级的多轴 GUI 风格引擎**，不是任意 CSS 换肤或重画 DSH。
- 0.1.9 已覆盖配色、字体、圆角、边框、阴影、表面、组件填充、壁纸与氛围；仍不能改变侧栏/主栏结构、左右消息流、头像、消息尾巴、工具调用 DOM 或顶部/底部导航。
- 当前契约仍为 `hostDensityTokens: false`、`hostTranscriptWidth: false`、`hostMessageFlow: false`；`renderLayoutCss()` 的 compat layer 为空。
- 0.2.0 分为 L0–L7。L5 拆成 **L5a Studio Decoration**（Livery 自有页面）和 **L5b Shell Decoration**（必须依赖正式冻结的宿主 slot）。当前没有 L5b slot，因此 0.2.0 MVP 不能把宿主级 HUD/RPG 装饰作为卖点。
- 保留全部 28 套风格；从现有风格中选择 4 套作为 v2 reference archetype（graphite / clay / cinnabar / rice-paper 候选映射），不新增第 29–32 套，也不缩减到 4 套。
- Manifest v2 使用完整 `meta + variants + typography + compat + presentation`，只允许注册 recipe ID；catalog wire 在 0.2.0 保持 v1，以可选字段扩展，避免 HMR 旧客户端被强制版本拒绝。
- 深度能力（L5b–L7）只允许 exact-certified adapter；compatibility fallback 必须强制屏蔽，未知宿主不得按版本号继承 slot/role。
- 不使用 semantic `data-dsh-part` 宿主 selector；只接受 token、service、slot。若未来必须引入，先修改 `AGENTS.md` 并建立 contract 精确 allowlist，不能沿用任意 `data-*` 后代选择器。
- 四态：`Full` / `Inherited` / `Degraded` / `Unavailable`；主动选择 `host`/`stock`/`none` 是 Inherited，不自动把所有风格标为 Degraded。
- 装饰是“Client 内置 renderer + catalog recipe ID/参数”，不是每套风格复制 SVG；geometry 与 material 拆轴，材质缺失不让整包 surface 回退。
- 当前 client/host gzip 余量极小，0.2.0 不先提高预算；recipe 去重、catalog 只存 ID，必要时先把 audit 明细移出 runtime catalog。

## Decision

0.2.0 should move Livery from a **token collection with component fills** to a
**capability-aware, safely degrading multi-axis GUI style engine**:

- richer visual languages (HUD, social, comic, ornate) through palette,
  typography, geometry, material, component recipes and plugin-owned decoration;
- every deep capability is declared, capability-gated and has a fixed fallback;
- host navigation structure and message DOM remain host-owned;
- arbitrary CSS and private DOM selectors are explicitly out of scope.

The public promise is **visual-language expansion**, not a DSH rewrite.

## Current boundary (0.1.9)

The current frozen contract still exposes only token-level visual hooks. For both
`0.2.1-rc.2` and `0.2.2-rc.3`:

```text
themeCss:            true
hostFontFamily:      true
fontRoleHooks:       true
surfaceMaterial:     true
hostDensityTokens:   false
hostTranscriptWidth: false
hostMessageFlow:     false
```

Evidence: [`contracts/dsh/0.2.2-rc.3/contract.json`](../../contracts/dsh/0.2.2-rc.3/contract.json),
`capabilities`.

What 0.1.9 can change safely:

- light/dark palette and semantic colours;
- UI/content/code font stacks and type scale;
- global radius, pills, square and `superellipse()` geometry;
- border colours/elevation, soft/hard/brutal shadows;
- glass, paper, terminal, editorial and poster surface recipes;
- sidebar, composer, generic bubble and selector fills through
  `CHROME_TOKEN_NAMES` in [`src/core/chrome.ts`](../../src/core/chrome.ts);
- wallpaper, frost and atmosphere layers.

What it cannot change:

- sidebar/main/right-column structure or position;
- contact/session/detail multi-column layouts;
- user vs assistant alignment, avatars, metadata or bubble tails;
- tool-call/thinking/attachment DOM grouping;
- per-component cut corners or arbitrary decoration nodes in host components;
- top navigation, bottom dock or HUD information architecture.

The current `renderLayoutCss()` only establishes the empty compat layer; it emits
no host layout rules. See [`src/core/layout.ts`](../../src/core/layout.ts).

The current frozen client API documents only the `settingsSection` slot and the
`localeNamespace`; there is no certified `shell.overlay`, message frame or shell
decoration slot. See `clientApi.slots` in the same contract.

## Goals and non-goals

### Goals

1. Make the visual difference between styles structural at the **style-system**
   level (geometry, material, component relationships, owned decoration), not
   just colour/font substitutions.
2. Keep every capability explicit: declared by the manifest, resolved against the
   host contract, rendered as declared + effective, and tested when degraded.
3. Keep host navigation, message content, accessibility and streaming owned by
   DSH.
4. Preserve older manifests through a one-way v1 → v2 migration while retaining
   all 28 existing styles.
5. Ship four **reference archetypes** selected from existing styles; do not
   shrink the catalog and do not add new styles merely to prove the system.

### Non-goals

- Arbitrary CSS skins, remote CSS, `@font-face`, remote decoration assets.
- Replacing or cloning the DSH sidebar, composer or transcript.
- Selecting host DOM by class, hashed name, `nth-child`, `data-*` guesses or
  MutationObserver.
- Claiming QQ-style left/right messages or HUD navigation before upstream ships
  stable structure APIs.
- Automatically granting deep capabilities to unknown 0.2.x hosts.
- Host component selectors, including public-looking `data-dsh-part` attributes;
  see [Semantic selectors](#semantic-selectors-not-proposed).

## Layer model

| Layer | Responsibility | 0.2.0 status | Capability source |
|---|---|---|---|
| L0 | exact host, adapter, contract, fail-closed gate | required | generated registry |
| L1 | palette and semantic tokens | extend | `themeCss` |
| L2 | typography, font roles and scale | extend | `hostFontFamily`, `fontRoleHooks` |
| L3 | geometry, border, elevation and material | split and extend | token-only; `surfaceMaterial` for translucency |
| L4 | component chrome recipes | extend | 8 consumed fill tokens |
| L5a | Studio Decoration on Livery-owned pages | ship | Livery-owned UI only |
| L5b | Shell Decoration over the DSH shell | conditional | proposed frozen `shell.overlay` slot |
| L6 | host visual roles (message/user/assistant/frame) | blocked | proposed host role tokens/slots |
| L7 | structural composition (navigation/message flow) | blocked | proposed layout recipe API |

**L5a is not a host theme capability.** It may decorate the gallery, wallpaper
workbench and Livery settings pages. It must not be shown in Host Preview or
described as a DSH shell theme.

**L5b is not part of MVP unless a supported host exposes a certified slot.**
Without one, `ornament`/`texture` over the shell compile to `none`; the four
reference styles still ship with palette, typography, geometry, material and
component chrome.

Each style must expose the effective level in the catalog and gallery:

```text
Palette: Full
Surface: Full
Decoration: Inherited or Full
Message roles: Inherited or Degraded
Navigation structure: Inherited or Degraded
```

The preview must not imply L5b/L6/L7 behavior when those layers are inherited or
degraded.

## Manifest v2

`schemaVersion: 2` applies to the **livery manifest**, not to the host contract or
the compiled catalog protocol. The current `SCHEMA_VERSION = 1` is shared across
surfaces and must be split before v2 lands:

```ts
export const MANIFEST_SCHEMA_VERSION = 2
export const CATALOG_SCHEMA_VERSION = 1 // host/client wire format, independent
export const PRESET_SCHEMA_VERSION = 1  // portable preset format, independent
```

The v2 manifest is a complete manifest, not a fragment. It retains the current
required fields and replaces the flat `layout` object with `presentation`:

```json
{
  "schemaVersion": 2,

    "description": {

      "en-US": "Near-square tactical panels, hard outlines and static scanlines."
    },
    "tags": ["tech", "cool"],
    "order": 251
  },
  "variants": {
    "light": {
      "seeds": {
        "accent": "#1f6feb",
        "secondary": "#34d399",
        "surface": "#eef2f6",
        "text": "#0b1220"
      }
    },
```

Rules:

- Only registered recipe IDs; no CSS, selectors, HTML, SVG strings, URLs or
  arbitrary lengths.
- Every recipe declares required/optional capabilities, fallback, media-policy
  behavior and a budget.
- The compiler emits **declared** and **effective** presentation separately.
- Missing capabilities follow a fixed fallback table; no DOM guessing.
- `navigation.structure` and `messages.flow` may only be `host`/`stock` until
  upstream capabilities exist; requesting more yields a diagnosed degradation.
- `surface` is not a single v2 field. Geometry, border, elevation and material
  are separate axes so a missing material capability cannot erase shape/border.
- The v1 `surfaceStyle` recipe remains readable through a normalizer, but its
  effective result is computed per sub-axis.

### v1 → v2 migration

All 28 built-in manifests remain v1 for 0.2.0. A normalizer converts them into the
single internal `NormalizedManifest` type; no runtime code branches on v1/v2.

| v1 | v2 internal |
|---|---|
| `layout.surfaceStyle` | `presentation.geometry` + `border` + `elevation` + `material` (recipe defaults) |
| `layout.chrome` | `presentation.chrome` |
| `layout.density` / `conversationWidth` / `messageFlow` | `presentation.host` diagnostic only; never claimed without capability |
| new | `texture`, `ornament`, `navigation`, `messages`, `motion` |

There will be two schema validators:

- `schemas/livery.schema.json` — v2 for new/edited manifests;
- `schemas/livery.v1.schema.json` (or equivalent frozen copy) — v1 for the
  existing built-ins during migration.

Both feed the same normalizer; the compiler never accepts an unnormalized object.
The 28 styles can be migrated to v2 in later commits without changing their IDs or
preview stems.

### Catalog wire decision

**Catalog remains schemaVersion 1 for 0.2.0.** New presentation data is additive
and optional:

```ts
interface CompiledLivery {
  // existing fields...
  readonly presentation?: {
    readonly declared: DeclaredPresentation
    readonly effective: EffectivePresentation
  }
}
```

- The client keeps requiring the current catalog envelope version; old clients
  ignore the optional field.
- A new client reads a v1 catalog with no presentation field as
  `Inherited` defaults; it never rejects a catalog solely for missing v2 fields.
- Required effective data also exists in compiler reports/audit artifacts, so a
  catalog producer bug cannot hide degradation.
- A future breaking catalog change requires a coordinated protocol bump, dual
  client/server tests and an HMR migration plan; it is not part of 0.2.0.

### Presets

Presets continue to store `styleId` and wallpaper state only. Presentation is a
property of the style; decoration is derived from the effective profile. If a
future release lets users export custom decoration/capability state, that is a
separate `PRESET_SCHEMA_VERSION = 2` with an explicit migration.

## Recipe registry

Capabilities are a single registry, not repeated string unions or hand-written
schema lists:

```ts
type CapabilityId = keyof typeof CAPABILITY_REGISTRY

interface PresentationRecipe<Id extends string> {
  readonly id: Id
  readonly layer: 'L3' | 'L4' | 'L5a' | 'L5b' | 'L6' | 'L7'
  readonly required: readonly CapabilityId[]
  readonly optional: readonly CapabilityId[]
  readonly fallback: Id | 'none' | 'host' | 'stock'
  readonly accessibility: {
    readonly forcedColors: 'hide' | 'system' | 'preserve'
    readonly reducedTransparency: 'hide' | 'solid' | 'preserve'
    readonly reducedMotion: 'static' | 'hide' | 'preserve'
  }
  readonly budget: {
    readonly cssBytes: number
    readonly catalogBytes?: number
    readonly svgPrimitives?: number
  }
}

interface ComponentRecipe {
  readonly navigation: RecipeId
  readonly composer: RecipeId
  readonly bubble: RecipeId
  readonly selector: RecipeId
  readonly floating: RecipeId
  readonly frame: RecipeId
}
```

`CapabilityId` is generated from one registry used by types, schema generation,
compiler, client and audit. This fixes the existing drift where
`host-font-role-hooks` exists in types but is missing from the schema enum.

Component recipes may only author tokens the host actually consumes. A recipe
named `game-bubble` does not acquire tails, avatars or alignment; those require
L6/L7 capabilities.

### Effective presentation states

Effective state is computed only from capabilities the manifest actually
requested:

| State | Meaning |
|---|---|
| `Full` | every requested recipe is effective |
| `Inherited` | manifest explicitly asks for `host` / `stock` / `none`; not a failure |
| `Degraded` | manifest requests a deeper recipe and a declared fallback is used |
| `Unavailable` | a required base capability is missing; the style falls back to stock |

L6/L7 not existing is **not** a reason to mark every style Degraded. A manifest
that declares `navigation.structure: "host"` and `messages.flow: "stock"` is
Inherited. Only a manifest that requests `social`/`alternating-bubbles` and lacks
the capability is Degraded.

## Catalog profile identity

The current `catalogProfileId` hashes only the token contract and the current
capability vector. That is insufficient once presentation, slots and decoration
exist: two hosts with different L5 capabilities must not share a profile.

The 0.2.0 profile hash must include:

- manifest/presentation grammar version and compiler version;
- declared capability vector (including slot/role hashes, not just booleans);
- certified slot/role contract hashes and stacking semantics;
- decoration grammar version and primitive allowlist version;
- layout recipe contract/version;
- host facts that change declared→effective results;
- preview grammar version if previews are profile-scoped.

`catalog-profile-overrides.json` validation must compare these fields, not a
free-text reason alone. An override is invalid if any presentation-affecting hash
differs. Exact-certified adapters alone may expose L5b–L7; compatibility fallback
masks these layers and reports the mask.

## Exact-certified depth and compatibility fallback

Deep capabilities are **exact-certified only**. For 0.2.0:

- L5b–L7 are available only for adapters whose loader/host/client API hashes
  match a frozen contract and whose slot/role capability has been certified.
- A compatibility-fallback adapter may load palette/typography/surface/chrome
  (L1–L4) but must force L5b = none, L6 = inherited, L7 = inherited.
- The current runtime boot path must not choose an adapter from a version string
  alone for deep capabilities. The minimum acceptable 0.2.0 rule is
  exact-certified-or-masked; the preferred long-term rule is a trusted runtime
  contract fingerprint with all three API hashes matching before any deep layer
  opens.
- Unknown hosts fail closed for unverified depth; no “same 0.2.x” inheritance.

## L5a and L5b decoration

### L5a — Studio Decoration

Livery-owned pages may use richer decoration without a host slot:

- gallery/wallpaper/settings panels may use decorative frames, grids or
  editorial rules;
- these are React/DOM nodes owned by Livery, cleaned up by `ctx.effect`;
- they are still subject to accessibility, performance and no-remote-assets
  rules;
- they are labeled **Studio Showcase**, not Host Preview, and cannot be used as
  evidence of DSH shell coverage.

### L5b — Shell Decoration

A shell decoration tree may be rendered only through a frozen, public slot such
as the proposed `shell.overlay`:

```tsx
<div data-dsh-livery-decoration aria-hidden="true" inert>
  <svg focusable="false">...</svg>
</div>
```

Requirements:

- `pointer-events: none`, `aria-hidden`, `inert`; never in the accessibility tree;
- never above Modal/Toast/Tooltip/HoverCard; no extreme z-index;
- official stacking contract must place the slot below every floating surface;
- no host DOM queries, no MutationObserver, no React node movement;
- no text, remote image or font;
- hide under `forced-colors`;
- hide or reduce under `prefers-reduced-transparency`;
- fully static under `prefers-reduced-motion`;
- if the slot capability or stacking contract is absent, compile
  `ornament: none` / `texture: none`.

The current contract has no such slot. The existing `shell.overlay` type only
says it is above the columns and click-through; that does **not** prove it is
below every Modal/Toast/Tooltip. The slot name, owner props, scope, lifecycle and
stacking must be frozen and hash-bound before L5b ships.

### Decoration data model

Decoration is **code + bounded data**, not per-style SVG blobs:

- Client ships a small set of shared decoration renderers;
- manifest/catalog stores only recipe IDs and bounded parameters;
- per-style geometry is deduplicated by recipe, not copied 28 times;
- primitives are limited to `line`, `rect`, `circle`, `polyline` and
  `pathId` from a frozen path registry;
- arbitrary path strings, `foreignObject`, `filter`, `href`, event attributes and
  text are forbidden;
- fill/stroke reference compiler-generated private tokens only;
- an independent decoration audit validates primitive count, token references,
  IDs and no-remote-data before compilation;
- one frame overlay per page; no infinite animation; no scroll-frame updates.

Lifecycle requirements:

- slot registration and disposal are `ctx.effect`-owned;
- HMR replaces or reuses exactly one overlay and never duplicates it;
- preview/cancel/apply/restore-stock are atomic;
- disable/uninstall leaves zero decoration nodes, styles or observers;
- late/removed slot declarations force a new effective result, not a stale one.

## Reference styles

0.2.0 **retains all 28 styles**. Four existing styles are refactored as v2
reference archetypes; the final mapping is reviewable, but the release does not
add a 29th style or shrink to four:

| Archetype | Candidate existing style | Planned visual focus |
|---|---|---|
| Tactical HUD | `graphite` | angular geometry, hard outline, terminal labels, static grid |
| Social Blue | `clay` | rounded controls, soft bubbles, tinted rail, humanist type |
| Comic Bubble | `cinnabar` | heavy outlines, large radii, high-contrast blocks, display type |
| Ornate RPG | `rice-paper` | serif/display pairing, engraved rules, page-level ornament |

The remaining 24 styles stay v1-normalized and continue to work. New recipes are
assigned to the full set only after the four archetypes pass the gates. The final
mapping may change after visual review; the invariant is **no count reduction,
no count inflation to prove the system**.

Host Preview shows only effective host capabilities. Studio Showcase may show
Livery-owned decoration, clearly labeled “not a DSH shell preview”.

## Degradation contract

| Requested capability | Missing host capability |
|---|---|
| L5b ornament | `none` |
| L5b texture overlay | `none` |
| navigation appearance | `plain` |
| navigation structure | `host` |
| message role styling | generic bubble |
| message flow | `stock` |
| transcript width | `host` |
| density | `host` |
| material | `solid` (geometry/border/elevation preserved) |
| surface aggregate (v1) | per-sub-axis fallback, never whole-style solid unless required |
| motion | `static` |
| base theme CSS | style unavailable → stock |

Private DOM selectors and semantic part selectors are never a fallback.

## Acceptance gates

### Structure and security

- 0 hashed-class selectors, 0 `!important`, 0 host-private selectors.
- 0 semantic part selectors and 0 arbitrary `data-*` descendant selectors.
- 0 document-wide MutationObserver; 0 host node wrapping/moving.
- 0 remote fonts/assets/URLs; decoration primitives are local and bounded.
- every new slot/role enters the frozen contract and API hash.
- exact-certified only for L5b–L7; compatibility fallback masks them.
- missing capability produces deterministic declared/effective output.
- unknown hosts do not acquire L5b–L7 by version number.

### Visual

- 1440 / 1200 / 1024 / 767 / 600 widths; light/dark.
- Web and Desktop renderer.
- wallpaper off/on; stock/full/inherited/degraded states.
- Tactical HUD, Social Blue, Comic Bubble, Ornate RPG archetypes.
- Settings Modal, Menu, Tooltip, Toast.
- long messages, code blocks, tool calls, errors.
- zh/en and 200% zoom.
- Host Preview vs Studio Showcase labels are visually explicit.

### Accessibility

- decorations hidden under `forced-colors`;
- blur/mix-blend disabled under reduced transparency;
- scanning/pulsing disabled under reduced motion;
- decoration outside the accessibility tree;
- colour never the only state signal;
- layout recipes preserve DOM/reading order.

### Lifecycle

- exact host with slot and exact host without slot;
- compatibility-fallback host masks L5b–L7;
- preview, cancel, apply, restore stock;
- HMR old/new client overlap and no duplicate overlay;
- slot late declaration, re-declaration and disappearance;
- multiple tabs and Desktop windows;
- plugin disable, uninstall and reinstall;
- overlay never intercepts clicks;
- Modal, Toast, Tooltip, Menu, HoverCard stacking;
- no stock-decoration first-frame flash;
- all previously declared hosts continue to pass.

### Performance

- ≤16 SVG primitives per decoration recipe;
- decoration geometry deduplicated per recipe in the Client;
- catalog stores IDs/parameters only, not per-style SVG;
- one frame overlay per page;
- no unbounded animation, no scroll-frame decoration updates;
- no per-message observer;
- catalog/client/host gzip and first-paint remain hard gates;
- theme switch must not cause visible CLS;
- do not raise existing gzip limits first; remove audit detail from runtime
  catalog or dedupe payloads before discussing a budget increase.

Current 0.1.9 headroom is already tight: client gzip 60,356 / 61,440 B and host
gzip 353,844 / 368,640 B; catalog cap 1,768,384 B. A 2 KiB/style decoration
payload multiplied by 28 is not acceptable; IDs and shared renderers are.

## Upstream requests

To unlock L6/L7, DSH should expose and freeze:

### Message-role tokens

```css
--dsh-message-user-fill
--dsh-message-user-label
--dsh-message-user-border
--dsh-message-user-radius
--dsh-message-assistant-fill
--dsh-message-assistant-label
--dsh-message-assistant-border
--dsh-message-assistant-radius
--dsh-message-group-gap
--dsh-message-avatar-size
```

### Layout recipe API

```ts
interface AppearanceLayoutRecipe {
  shell: 'stock' | 'social' | 'game-hud'
  navigation: 'sidebar' | 'compact-rail' | 'top-tabs' | 'bottom-dock'
  conversation: {
    flow: 'document' | 'alternating-bubbles'
    avatars: 'none' | 'compact'
    metadata: 'inline' | 'stacked'
  }
}
```

The upstream contract must also define:

- state ownership and who can preview/apply/rollback;
- first-frame boot participation;
- conflict priority when multiple plugins request layouts;
- narrow-screen and unsupported-platform fallback;
- whether a user’s manual layout preference outranks a theme;
- the audit/evidence fields that prove the applied recipe.

### Visual frame slots

Proposed names (not current contract):

```text
conversation.message.frame
conversation.message.leading-decoration
conversation.message.trailing-decoration
conversation.composer.frame
sidebar.session.decoration
shell.background
shell.decoration
```

Owner props for message frames must be visual-only:

```ts
interface MessageVisualOwnerProps {
  role: 'user' | 'assistant' | 'system' | 'tool'
  groupedBefore: boolean
  groupedAfter: boolean
  state: 'streaming' | 'complete' | 'error'
}
```

The host must not pass message text, tool payload, privacy data or business
actions to a decoration plugin. Stacking must be formally specified below
Modal/Toast/Tooltip/Menu/HoverCard.

### Semantic selectors: not proposed

This proposal **does not** request `data-dsh-part` selectors. Tokens, services and
slots are the only accepted extension surface.

If a future upstream path requires semantic selectors, it needs an explicit
`AGENTS.md` change plus an exact contract allowlist, audit support for only those
frozen names, and no generic `data-*` descendant permission. Until then, semantic
parts are out of scope.

## 0.2.0 release slicing

### MVP (repository-only)

- manifest v2 + v1 normalizer for all 28 styles;
- split manifest/catalog/preset schema versions;
- typed recipe registry with required/optional capabilities and a11y policy;
- geometry/border/elevation/material split;
- finer surface and component chrome;
- **L5a Studio Decoration only**;
- four reference archetypes refactored from existing styles;
- Full/Inherited/Degraded/Unavailable state in gallery DNA and self-check;
- exact-certified depth and compatibility-fallback mask;
- security, a11y, lifecycle and performance gates;
- host navigation and message structure still native.

L5b is **not in MVP unless at least one supported host exposes a certified slot
and stacking contract**. If it does, it ships as an additional capability and
must pass the full host matrix; it is not a marketing prerequisite for 0.2.0.

### 0.2.x after message-role tokens

- user/assistant independent fills, radii, borders and padding;
- closer social bubbles; still host-owned flow.

### After layout/frame APIs

- left/right message flow;
- avatars and tails;
- top tabs/bottom dock/HUD shell;
- contact/session/detail columns;
- per-component cut corners and decorative frames.

If upstream APIs land during the 0.2.0 cycle and pass independent certification,
they may ship in 0.2.0; otherwise they ship as Degraded/Inherited, never as private
DOM replacements.

## Risks and open questions

1. **Catalog growth**: optional presentation fields still consume bytes; keep them
   out of runtime catalog until needed, or store IDs only.
2. **Host bundle**: L5a renderer and optional L5b code add client bytes; decide
   code/data split before setting the 2 KiB budget.
3. **Slot availability**: without a certified slot, L5b is `none`; do not count
   it as a 0.2.0 feature.
4. **Schema migration**: v1 and v2 must be validated and normalized identically;
   the existing built-ins stay v1 during the first 0.2.0 pass.
5. **Preview truthfulness**: Host Preview must show effective profile; Studio
   Showcase must be labeled and must not use host chrome.
6. **Host version matrix**: deep capabilities require exact contracts; no 0.2.x
   inheritance.
7. **Catalog/profile override**: validate capability/slot hashes, not prose.

## Acceptance wording

Safe external wording:

> DSH Livery 0.2.0 upgrades the theme system into a multi-axis GUI visual recipe
> engine: palette, typography, surface geometry, component fills and
> safely-degrading Studio decoration. HUD, social, comic and ornate styles are no
> longer only colour changes, while host navigation and message structure remain
> owned by DSH. Shell-level decoration appears only on hosts that certify a
> frozen decoration slot.

Unsafe wording:

- complete DSH rewrite;
- arbitrary CSS skinning;
- arbitrary navigation replacement;
- arbitrary chat DOM modification;
- QQ-style left/right bubbles on every host;
- HUD/RPG shell decoration on every current host;
- automatic compatibility with uncertified DSH builds.
