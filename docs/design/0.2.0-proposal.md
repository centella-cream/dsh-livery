# DSH Livery 0.2.0 proposal — capability-aware GUI style engine

> **Status: proposal, not implemented and not released.** This note defines the
> intended 0.2.0 direction. It does not change the 0.1.9 manifest, host contract,
> catalog, published evidence or supported-host claims. A proposal is not an
> acceptance claim; each capability needs a frozen contract, implementation,
> tests and host evidence before it ships.

## Decision

0.2.0 should move Livery from a **token collection with component fills** to a
**capability-aware, safely degrading multi-axis GUI style engine**:

- richer visual languages (HUD, social, comic, ornate) through palette,
  typography, geometry, material, component recipes and plugin-owned decoration;
- every deep capability is declared, capability-gated and has a fixed fallback;
- host navigation structure and message DOM remain host-owned;
- arbitrary CSS and private DOM selectors are explicitly out of scope.

The public promise is **visual-language expansion**, not a DSH rewrite.

## Current boundary (0.1.9)

The current frozen contract still exposes only token-level visual hooks. For both
`0.2.1-rc.2` and `0.2.2-rc.3`:

```text
themeCss:            true
hostFontFamily:      true
fontRoleHooks:       true
surfaceMaterial:     true
hostDensityTokens:   false
hostTranscriptWidth: false
hostMessageFlow:     false
```

Evidence: [`contracts/dsh/0.2.2-rc.3/contract.json`](../../contracts/dsh/0.2.2-rc.3/contract.json),
`capabilities`.

What 0.1.9 can change safely:

- light/dark palette and semantic colours;
- UI/content/code font stacks and type scale;
- global radius, pills, square and `superellipse()` geometry;
- border colours/elevation, soft/hard/brutal shadows;
- glass, paper, terminal, editorial and poster surface recipes;
- sidebar, composer, generic bubble and selector fills through
  `CHROME_TOKEN_NAMES` in [`src/core/chrome.ts`](../../src/core/chrome.ts);
- wallpaper, frost and atmosphere layers.

What it cannot change:

- sidebar/main/right-column structure or position;
- contact/session/detail multi-column layouts;
- user vs assistant alignment, avatars, metadata or bubble tails;
- tool-call/thinking/attachment DOM grouping;
- per-component cut corners or arbitrary decoration nodes in host components;
- top navigation, bottom dock or HUD information architecture.

The current `renderLayoutCss()` only establishes the empty compat layer; it emits
no host layout rules. See [`src/core/layout.ts`](../../src/core/layout.ts).

The current frozen client API documents only the `settingsSection` slot and the
`localeNamespace`; there is no certified `shell.overlay`, message frame or shell
decoration slot. See `clientApi.slots` in the same contract.

## Goals and non-goals

### Goals

1. Make the visual difference between styles structural at the **style-system**
   level (geometry, material, component relationships, owned decoration), not
   just colour/font substitutions.
2. Keep every capability explicit: declared by the manifest, resolved against the
   host contract, rendered as declared + effective, and tested when degraded.
3. Keep host navigation, message content, accessibility and streaming owned by
   DSH.
4. Preserve older manifests through a one-way v1 → v2 migration.
5. Ship four reference styles first; migrate the remaining 28 only after the
   recipe system is stable.

### Non-goals

- Arbitrary CSS skins, remote CSS, `@font-face`, remote decoration assets.
- Replacing or cloning the DSH sidebar, composer or transcript.
- Selecting host DOM by class, hashed name, `nth-child`, `data-*` guesses or
  MutationObserver.
- Claiming QQ-style left/right messages or HUD navigation before upstream ships
  stable structure APIs.
- Automatically granting deep capabilities to unknown 0.2.x hosts.

## Layer model

| Layer | Responsibility | 0.2.0 status | Capability source |
|---|---|---|---|
| L0 | exact host, adapter, contract, fail-closed gate | required | existing generated registry |
| L1 | palette and semantic tokens | extend | `themeCss` |
| L2 | typography, font roles and scale | extend | `hostFontFamily`, `fontRoleHooks` |
| L3 | geometry and material recipes | refactor/extend | token-only; `surfaceMaterial` for glass |
| L4 | component chrome recipes | extend | 8 consumed fill tokens |
| L5 | plugin-owned decoration | new, gated | proposed `shell.overlay` slot |
| L6 | host visual roles (message/user/assistant/frame) | blocked | proposed host role tokens |
| L7 | structural composition (navigation/message flow) | blocked | proposed layout recipe API |

Each style must expose the effective level in the catalog and gallery:

```text
Palette: Full
Surface: Full
Decoration: Full
Message roles: Degraded
Navigation structure: Host
```

The preview must not imply L6/L7 behavior when those layers are degraded.

## Manifest v2

`schemaVersion: 2` applies to the **livery manifest**, not to the host contract or
the compiled catalog protocol. The current `SCHEMA_VERSION = 1` is shared across
surfaces and should be split before v2 lands:

```ts
export const MANIFEST_SCHEMA_VERSION = 2
export const CATALOG_SCHEMA_VERSION = 1 // host/client wire format, independent
export const PRESET_SCHEMA_VERSION = 1  // portable preset format, independent
```

The v2 manifest is recipe-only:

```json
{
  "schemaVersion": 2,
  "id": "neon-tactical",
  "presentation": {
    "surface": "hud-cut",
    "chrome": "hud-tactical",
    "texture": "scanlines-subtle",
    "ornament": "hud-corners",
    "navigation": {
      "structure": "host",
      "appearance": "accent-rail"
    },
    "messages": {
      "flow": "stock",
      "user": "token-bubble",
      "assistant": "stock"
    },
    "motion": "static"
  }
}
```

Rules:

- Only registered recipe IDs; no CSS, selectors, HTML, SVG strings, URLs or
  arbitrary lengths.
- Every recipe declares its capability, fallback and performance grade.
- The compiler emits **declared** and **effective** presentation separately.
- Missing capabilities follow a fixed fallback table; no DOM guessing.
- `navigation.structure` and `messages.flow` may only be `host`/`stock` until the
  corresponding upstream capabilities exist.
- v1 manifests are read by a migration layer and compiled to the v2 internal
  model; the catalog wire format can stay at v1 until a deliberate protocol bump.

Proposed v1 → v2 mapping:

| v1 | v2 |
|---|---|
| `layout.surfaceStyle` | `presentation.surface` |
| `layout.chrome` | `presentation.chrome` |
| `layout.density` / `conversationWidth` / `messageFlow` | `presentation.host` diagnostic only; never claimed without capability |
| new | `presentation.texture`, `ornament`, `navigation`, `messages`, `motion` |

The exact names are reviewable; the invariant is **IDs and declared/effective
results, never executable styling**.

## Recipe registry

Introduce a registry with typed recipes and capability metadata:

```ts
interface PresentationRecipe<Id extends string> {
  readonly id: Id
  readonly layer: 'L3' | 'L4' | 'L5' | 'L6' | 'L7'
  readonly capability: string
  readonly fallback: Id | 'none' | 'host' | 'stock'
  readonly budget: { cssBytes: number; primitives?: number }
}

interface ComponentRecipe {
  readonly navigation: RecipeId
  readonly composer: RecipeId
  readonly bubble: RecipeId
  readonly selector: RecipeId
  readonly floating: RecipeId
  readonly frame: RecipeId
}
```

Component recipes may only author tokens the host actually consumes. A recipe
named `game-bubble` does not acquire tails, avatars or alignment; those require
L6/L7 capabilities.

## Owned decoration

### Allowed design

A plugin-owned decoration tree may be rendered only through a frozen, public
slot. The proposed shape:

```tsx
<div data-dsh-livery-decoration aria-hidden="true" inert>
  <svg focusable="false">...</svg>
</div>
```

It can express:

- HUD corner brackets, static scanlines, dot/circuit grids, nameplates;
- comic outlines and page-level caption shapes;
- RPG corner ornaments and frame lines;
- social background dots and soft pattern fields.

Requirements:

- `pointer-events: none`, `aria-hidden`, `inert`; never in the accessibility tree;
- never above Modal/Toast/Tooltip/HoverCard; no extreme z-index;
- no host DOM queries, no MutationObserver, no React node movement;
- no text, remote image or font;
- hide under `forced-colors`;
- hide or reduce under `prefers-reduced-transparency`;
- fully static under `prefers-reduced-motion`;
- if the slot capability is absent, compile `ornament: none`.

The current contract has no such slot. **Do not use an undocumented slot because
a local `.d.ts` file exposes it.** The slot name, type, scope, owner shape and
lifecycle must be frozen in the client contract and its hash before L5 ships.

For 0.2.0 MVP, decoration inside Livery-owned pages (gallery, wallpaper
workbench) is allowed without a host slot; decoration over the host shell is not.

## Reference styles

Use four reference styles to prove the system before migrating all 28:

### Tactical HUD

- near-square geometry, hard borders, local glow;
- technical/monospace labels;
- static scanlines, grid and corner brackets;
- dark rail, high-signal state colours;
- host navigation and message structure unchanged.

### Social Blue

- QQ-like blue language, rounded controls, soft bubbles, tinted rail;
- humanist or rounded type;
- lighter elevation;
- generic bubble fill/background only; no left/right flow guarantee.

### Comic Bubble

- heavy outlines, large radii, high-contrast blocks;
- display type and active hierarchy;
- real comic panels only in Livery-owned pages;
- host messages keep the generic bubble token until L6 exists.

### Ornate RPG

- metal/arcane/classical palettes;
- hard shadows, engraved lines, corner ornaments;
- serif/display combinations;
- page-level frame ornament, no bitmap skins or remote assets.

Only after these four pass the same gates should recipes be assigned across the
existing catalog.

## Degradation contract

| Requested capability | Missing host capability |
|---|---|
| ornament | `none` |
| texture overlay | `none` |
| navigation appearance | `plain` |
| navigation structure | `host` |
| message role styling | generic bubble |
| message flow | `stock` |
| transcript width | `host` |
| density | `host` |
| surface material | `solid` |
| motion | `static` |
| base theme CSS | style unavailable → stock |

Private DOM selectors are never a fallback.

## Acceptance gates

### Structure and security

- 0 hashed-class selectors, 0 `!important`, 0 host-private selectors.
- 0 document-wide MutationObserver; 0 host node wrapping/moving.
- 0 remote fonts/assets/URLs; decoration recipes are local and bounded.
- every new slot/role enters the frozen contract and API hash.
- missing capability produces deterministic declared/effective output.
- unknown hosts do not acquire L5–L7 by version number.

### Visual

- 1440 / 1200 / 1024 / 767 / 600 widths; light/dark.
- Web and Desktop renderer.
- wallpaper off/on; stock/full/degraded states.
- Tactical HUD, Social Blue, Comic Bubble, Ornate RPG references.
- Settings Modal, Menu, Tooltip, Toast.
- long messages, code blocks, tool calls, errors.
- zh/en and 200% zoom.

### Accessibility

- decorations hidden under `forced-colors`;
- blur/mix-blend disabled under reduced transparency;
- scanning/pulsing disabled under reduced motion;
- decoration outside the accessibility tree;
- colour never the only state signal;
- layout recipes preserve DOM/reading order.

### Performance

- ≤16 SVG primitives per decoration recipe;
- ≤2 KiB compiled decoration data per style;
- one frame overlay per page;
- no unbounded animation, no scroll-frame decoration updates;
- no per-message observer;
- catalog/client/host gzip and first-paint remain hard gates;
- theme switch must not cause visible CLS.

Current headroom is already tight: client gzip 60,356 / 61,440 B and host gzip
353,844 / 368,640 B on 0.1.9. 0.2.0 must budget new recipes and decoration
explicitly, or reduce another payload before adding.

## Upstream requests

To unlock L6/L7, DSH should expose and freeze:

### Message-role tokens

```css
--dsh-message-user-fill
--dsh-message-user-label
--dsh-message-user-border
--dsh-message-user-radius
--dsh-message-assistant-fill
--dsh-message-assistant-label
--dsh-message-assistant-border
--dsh-message-assistant-radius
--dsh-message-group-gap
--dsh-message-avatar-size
```

### Layout recipe API

```ts
interface AppearanceLayoutRecipe {
  shell: 'stock' | 'social' | 'game-hud'
  navigation: 'sidebar' | 'compact-rail' | 'top-tabs' | 'bottom-dock'
  conversation: {
    flow: 'document' | 'alternating-bubbles'
    avatars: 'none' | 'compact'
    metadata: 'inline' | 'stacked'
  }
}
```

DSH renders the structure; Livery only requests a recipe. The host retains
responsive layout, keyboard order, landmarks, macOS title-bar avoidance,
virtualization, streaming and stock fallback.

### Visual frame slots

Proposed names (not current contract):

```text
conversation.message.frame
conversation.message.leading-decoration
conversation.message.trailing-decoration
conversation.composer.frame
sidebar.session.decoration
shell.background
shell.decoration
```

These replace only visual shells; message content, copy/feedback and streaming
remain host-owned.

### Stable semantic parts

If upstream chooses CSS anchors instead of slots, freeze and document:

```text
[data-dsh-part="message-row"]
[data-dsh-part="message-bubble"]
[data-dsh-role="user"]
[data-dsh-role="assistant"]
[data-dsh-part="composer"]
[data-dsh-part="sidebar"]
```

Each must be versioned, contract-snapshotted, lifecycle-guaranteed, independent
of parent-child shape and checked by contract diff.

## 0.2.0 release slicing

### MVP (repository-only)

- manifest v2 + v1 migration;
- split manifest/catalog/preset schema versions;
- registered presentation recipes;
- finer surface and component chrome;
- contract-certified owned decoration **only if a slot exists** (otherwise
  `ornament: none`);
- four reference styles;
- Full/Degraded/Unavailable state in gallery DNA and self-check;
- security, a11y and performance gates;
- host navigation and message structure still native.

### 0.2.x after message-role tokens

- user/assistant independent fills, radii, borders and padding;
- closer social bubbles; still host-owned flow.

### After layout/frame APIs

- left/right message flow;
- avatars and tails;
- top tabs/bottom dock/HUD shell;
- contact/session/detail columns;
- per-component cut corners and decorative frames.

If these upstream APIs land during the 0.2.0 cycle and pass independent
certification, they may ship in 0.2.0; otherwise they ship as Degraded, never as
private DOM replacements.

## Risks and open questions

1. **Catalog growth**: adding recipes to 28 styles can break the existing catalog
   JSON headroom; define a per-style recipe budget before migration.
2. **Host bundle**: L5 decoration adds client code; decide whether decoration
   recipes are code or data before committing to the 2 KiB/style budget.
3. **Slot availability**: without a certified slot, L5 shell decoration must be
   `none`; do not count it as a 0.2.0 feature.
4. **Schema migration**: v1 manifests and presets must remain readable; the
   preset schema may need its own version if presentation state enters exports.
5. **Preview truthfulness**: gallery previews must show effective levels, not
   the ideal declared recipe.
6. **Host version matrix**: new capabilities require new contract snapshots and
   evidence; do not infer them from a 0.2.x version string.

## Acceptance wording

Safe external wording:

> DSH Livery 0.2.0 upgrades the theme system into a multi-axis GUI visual recipe
> engine: palette, typography, surface geometry, component fills and
> safely-degrading page decoration. HUD, social, comic and ornate styles are no
> longer only colour changes, while host navigation and message structure remain
> owned by DSH.

Unsafe wording:

- complete DSH rewrite;
- arbitrary CSS skinning;
- arbitrary navigation replacement;
- arbitrary chat DOM modification;
- QQ-style left/right bubbles on every host;
- automatic compatibility with uncertified DSH builds.
