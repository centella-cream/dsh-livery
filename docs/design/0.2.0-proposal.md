# DSH Livery 0.2.0 proposal — capability-aware GUI style engine

> **Status: implemented design input shipped in the 0.2.0 release (2026-11-21);**
> The implemented visual scope is recorded in
> [`0.2.0-visual-language.md`](0.2.0-visual-language.md); structural layout items
> that require new host APIs remain marked as not implemented. This note is not
> an acceptance claim; capabilities are bound by frozen contracts, tests and
> evidence under `contracts/dsh/evidence/0.2.2/`.

## Confirmed decisions (2026-11-17)

- Catalog uses a **v2 protocol** in 0.2.0. There is no v1 projection from a
  0.2.0 host.
- 0.2.0 MVP ships **L5a Studio Decoration only**; L5b waits for a certified
  dedicated shell decoration slot.
- The four archetypes map to existing `graphite`, `clay`, `cinnabar` and
  `rice-paper`; all 28 styles remain.
- 0.2.0 accepts **exact-certified hosts only**; unknown 0.2.x hosts fail closed. A runtime fingerprint is required before any compatibility fallback returns, because L1–L4 also depend on loader/routes/services.
- Existing gzip/catalog budgets are hard limits; recipe dedupe and payload
  trimming are required.
- Semantic selectors are removed; only token/service/slot remain.
- **Cross-major HMR is not promised.** 0.1.9 Client ↔ 0.2.0 Host and 0.2.0
  Client ↔ 0.1.9 Host both require a reload/restart, not a mixed running pair.

## 摘要（中文）

- 0.2.0 定位是**能力感知、可安全降级的多轴 GUI 风格引擎**，不是任意 CSS 换肤或重画 DSH。
- 0.1.9 已覆盖配色、字体、圆角、边框、阴影、表面、组件填充、壁纸与氛围；仍不能改变侧栏/主栏结构、左右消息流、头像、消息尾巴、工具调用 DOM 或顶部/底部导航。
- 当前契约仍为 `hostDensityTokens: false`、`hostTranscriptWidth: false`、`hostMessageFlow: false`；`renderLayoutCss()` 的 compat layer 为空。
- 0.2.0 分为 L0–L7。L5 拆成：
  - **L5a Studio Decoration**：Livery 自有页面，使用 `studioDecoration`，不算宿主主题能力；
  - **L5b Shell Decoration**：等待专用 `shell.decoration` slot 和正式 stacking 契约，0.2.0 不启用。
- Manifest v2 只用于四套 archetype：`graphite`、`clay`、`cinnabar`、`rice-paper`；其余 24 套继续 v1，经 normalizer 进入同一内部模型。
- Catalog 在 0.2.0 直接升到 v2，携带 required presentation。**不提供 v1 projection**；跨 0.1.9↔0.2.0 的 HMR 不承诺，必须重启/刷新。新 Client 只接受 v2。
- **0.2.0 只接受 exact-certified host**；未知 0.2.x 不再走 compatibility fallback。L1–L4 也依赖 loader/路由/service 生命周期，不能用版本号推断。
- 深度能力（L5b–L7）只允许 exact-certified adapter；0.2.0 对未知宿主整体 fail closed。compatible-preview 在 runtime fingerprint 可用前不恢复。
- 不使用 semantic `data-dsh-part` 宿主 selector；只接受 token、service、slot。
- 四态按轴计算：`Full` / `Inherited` / `Degraded` / `Unavailable`；整体状态只是聚合摘要。
- 装饰是“Client 内置 renderer + manifest/catalog recipe ID/参数”，不复制 28 套 SVG；geometry 与 material 拆轴，材质缺失不让整包 surface 回退。
- 当前 client/host gzip 余量极小，0.2.0 不先提高预算；recipe 去重、catalog 只存 ID、audit 只保留固定大小摘要。
- Catalog 超限从当前 warn 改为 **hard fail**；Desktop sidebar tint parity 是 0.2.0 必过门禁。

## Decision

0.2.0 moves Livery from a **token collection with component fills** to a
**capability-aware, safely degrading multi-axis GUI style engine**. The public
promise is visual-language expansion, not a DSH rewrite.

### Policy status

Exact-only is a **proposed 0.2.0 policy**, not the current repository policy.
0.1.9 continues to use `>=0.2.1-rc.2 <0.3.0` with reviewed API-hash fallback.
Before 0.2.0 implementation freezes, the same change set must update
`AGENTS.md`, `package.json` `engines.dsh`/`dsh.compatibility.dshReleases`,
`docs/design/multi-version.md`, `docs/design/compatibility.md`, support matrix,
runtime boot gate, diagnostics and evidence. Until then no release claim may say
exact-only is already in force.

**Decision:** `engines.dsh` remains the reviewed 0.2 range as an
**installability** declaration only. It does not grant runtime compatibility.
All runtime acceptance, profile reuse and Catalog serving require exact
certified adapters. `dsh.compatibility.dshReleases` contains exact hosts only.
`release-check.mjs` must stop requiring fallback support and instead validate
the range/installability separately from the exact runtime gate.

The minimum policy migration is:

| Surface | Required change |
|---|---|
| `AGENTS.md` | replace range/fallback rule with exact-only + fingerprint restoration rule |
| `package.json` | keep `engines.dsh` as the reviewed 0.2 **installability** range; `dsh.compatibility.dshReleases` lists exact hosts only; runtime still exact-only |
| `multi-version.md` / `compatibility.md` | one authoritative policy, no dual wording |
| support matrix | exact scopes only; fallback status not claimed |
| `release-check.mjs` | validate the installability range separately from runtime exact-only; no fallback-required gate |
| `boot.ts` | reject unknown hosts before adapter selection; no version-string fallback |
| diagnostics | unknown host: install may succeed, boot fails closed; no compatible-preview success claim |
| evidence | exact-host matrix only |

## Goals and non-goals

### Goals

1. Make visual differences structural at the style-system level through
   geometry, material, component relationships and owned decoration.
2. Keep every capability explicit: declared, capability-gated, rendered as
   declared/effective, and tested when degraded.
3. Keep host navigation, message content, accessibility and streaming owned by
   DSH.
4. Preserve older manifests through a v1 → v2 normalizer while retaining all 28
   styles.
5. Refactor four existing styles as v2 reference archetypes; do not shrink or
   inflate the catalog.

### Non-goals

- Arbitrary CSS skins, remote CSS, `@font-face`, remote decoration assets.
- Replacing/cloning DSH sidebar, composer or transcript.
- Host DOM selectors by class, hashed name, `nth-child`, `data-*` guesses,
  semantic parts or MutationObserver.
- Claiming QQ left/right messages or HUD navigation before upstream APIs exist.
- Automatic deep capabilities for unknown 0.2.x hosts.
- Cross-major HMR compatibility.

## Layer model

| Layer | Responsibility | 0.2.0 status | Source |
|---|---|---|---|
| L0 | exact host, adapter, contract, fail-closed gate | required | generated registry |
| L1 | palette and semantic tokens | extend | `themeCss` |
| L2 | typography, font roles and scale | extend | `hostFontFamily`, `fontRoleHooks` |
| L3 | geometry, border, elevation and material | split/extend | token-only; `surfaceMaterial` for translucency |
| L4 | component chrome recipes | extend | 8 consumed fill tokens |
| L5a | Studio Decoration on Livery-owned pages | **ship** | `studioDecoration`; no host capability |
| L5b | Shell Decoration over the DSH shell | **deferred** | proposed `shell.decoration` slot |
| L6 | host visual roles (message/frame) | blocked | proposed host role tokens/slots |
| L7 | structural composition | blocked | proposed layout recipe API |

L5a is not a host theme capability. It decorates the gallery, wallpaper workbench
and Livery settings pages only. It never appears in Host Preview and does not use
`presentation.ornament`.

L5b is deferred. Without a certified `shell.decoration` slot and stacking
contract, shell `ornament`/`texture` compile to `none`; no overlay node is
created.

### v1 → v2 normalization

v1/v2.

| `layout.chrome` | `presentation.chrome` |
| `layout.density` | `presentation.density` (`host`; no v1 claim) |
| `layout.conversationWidth` | `presentation.transcriptWidth` (`host`; no v1 claim) |
| `layout.messageFlow` | `presentation.messages.flow` (`stock`; no v1 claim) |
| absent | `studioDecoration: none`, `ornament: none`, motion static |

Token ownership is disjoint: geometry owns radius/corner-shape; border owns
border colours/widths; elevation owns shadow/elevation tokens; material owns
backdrop filters/blur. No axis may author another axis's tokens; the compiler
rejects overlap. Explicit v2 fields override the v1 expansion per axis. A v1→v2
migration gate asserts that the 24 legacy styles keep identical rendered CSS,
token values, preview bytes, style ID and effective body hash; only catalog
presentation metadata may differ.
There are two validators:

- `schemas/livery.schema.json` for v2;
- a frozen v1 validator for the 24 legacy manifests during migration.

Both feed the same normalizer. The compiler never accepts an unnormalized object.
The four archetype manifests are migrated in the same change set; the other 24
can migrate later without ID/preview changes.

### Capability source of truth

v2 manifests **do not contain `compat.requiredCapabilities` or
`compat.optionalCapabilities`**. Declared capabilities are derived only from:

1. the base axes (palette/typography/material/media policy);
2. the selected recipe registry entries' `required`/`optional` sets;
3. the fixed presentation grammar.

v1 manifests still contain `compat` because their schema requires it, but the
normalizer treats it as **legacy metadata only**: it is validated for shape,
ignored for gating, and removed from the normalized model. This avoids two
authoritative capability sources. A migration test asserts that v1 `compat`
cannot change any effective capability or status.

The compiler emits `derivedCapabilities` and fails if a v2 manifest contains a
`compat` object, an unknown capability ID, or a recipe whose required set is not
present in the derived set.

### Bounded recipe parameters

Every recipe declares a **named parameter map** generated from one registry:

```ts
type RegistryId = keyof typeof PARAMETER_REGISTRIES

type RecipeParameterSpec =
  | { readonly type: 'enum'; readonly values: readonly [string, ...string[]]; readonly default?: string }
  | { readonly type: 'integer'; readonly min: number; readonly max: number; readonly default?: number }
  | { readonly type: 'ratio'; readonly min: number; readonly max: number; readonly default?: number }
  | { readonly type: 'id'; readonly registry: RegistryId; readonly default?: string }

interface RecipeParametersSchema {
  readonly properties: Readonly<Record<string, RecipeParameterSpec>>
  readonly required: readonly string[]
  readonly additionalProperties: false
  readonly maxProperties: number      // 0..4; zero-parameter recipes allowed
}
```

Registry meta-validation:

- `maxProperties` is an integer in 0..4 and equals `properties.length`; a
  zero-parameter recipe is valid.
- `required ⊆ properties`; duplicate required names rejected. A required property
  must not declare a default; an optional property may default and is expanded
  before canonical hashing. A required property without a supplied value is
  rejected.
- property names match `^[a-z][a-z0-9-]{0,31}$`; at most 4 properties.

- integer `min/max` are safe integers, `min <= max`; ratio `min/max` are finite
  in `[0,1]`, `min <= max`.
- `enum` has at least one value and no duplicates; `id` registry exists and has a
  fixed pattern/length; defaults pass the same check.
- The registry itself is meta-validated at build time; invalid schemas fail the
  compiler before any manifest is read.

Rules:

- `enum` must carry a non-empty `values`; `integer`/`ratio` must carry finite
  `min`/`max`; `id` must name a registered allowlist and obey its pattern/length.
- No arrays in 0.2.0. Scalar properties only; `maxItems` is not used.
- Unknown property names and missing required properties are rejected; required
  properties have no default, so omission cannot be masked.
- Defaults, when present, must satisfy the same bound/allowlist checks.
- Manifest validation, compiler audit and client runtime validation use the same
  generated schema; there is no hand-written second validator.
- The example `parameters: { "density": "subtle" }` is valid only when the recipe
  declares a `density` enum property with `subtle` in `values`.

The decoration primitive allowlist is fixed (`line`, `rect`, `circle`, `polyline`,
frozen `pathId`); no arbitrary path strings or SVG content.

## Catalog v2

The 0.2.0 host serves **only schemaVersion 2**. There is no v1 projection and no
`?catalog=2` negotiation. A 0.1.9 client cannot consume a 0.2.0 catalog; cross-
major HMR is explicitly unsupported and requires a reload/restart.

```ts
interface LiveryCatalogV2 {
  readonly schemaVersion: 2
  readonly grammar: {
    readonly catalog: 2
    readonly presentation: 2
    readonly decoration: 1
    readonly preview: 1
    readonly parameterSchema: 1
  }
  readonly grammarHash: string // sha256(canonical grammar)
  readonly catalogHash: string // sha256(canonical payload excluding catalogHash)
  readonly compilerVersion: string
  readonly adapterId: string
  readonly hostVersion: string
  readonly contractHash: string
  readonly catalogProfile: string
  readonly capabilities: CapabilityMap
  readonly previewsBase: string
  readonly liveries: readonly CompiledLiveryV2[]
}

interface RecipeInstance<Id extends string = string> {
  readonly id: Id
  readonly parameters: Readonly<Record<string, string | number>>
}

type RecipeRef = RecipeInstance | 'host' | 'stock' | 'none'

Recipe parameters are normalized before catalog hashing: keys sorted by UTF-8
code unit, defaults expanded from the recipe's generated schema, all values
validated, then canonical JSON (`JSON.stringify` with sorted keys and no
whitespace). The Catalog carries the normalized object, never a raw parameter
string; the same canonical bytes feed the livery hash and cache profile.

interface CompiledLiveryV2 {
  // existing compiled fields: id, css, hash, preview metadata...
  readonly presentation: {
    readonly axes: Readonly<Record<PresentationAxis, AxisPresentation>>
    readonly overall: AxisStatus
    readonly responsivePolicy: ResponsivePolicy
  }
  readonly auditSummary: AuditSummary
}

interface ResponsivePolicy {
  readonly breakpoints: readonly [999, 799, 599]
  readonly studioDecoration: {
    readonly full: 'width > 999'
    readonly reduced: '799 < width <= 999'
    readonly minimal: '599 < width <= 799'
    readonly none: 'width <= 599'
  }
}

// Runtime-only, never serialized into the static Catalog.
interface RuntimeAxisPresentation {
  readonly declared: RecipeRef
  readonly effective: RecipeRef
  readonly status: AxisStatus
  readonly missingCapabilities: readonly CapabilityId[]
  readonly fallbackReason?: string
  readonly reason?: 'container-too-narrow'
}

interface MediaState {
  readonly forcedColors: boolean
  readonly reducedTransparency: boolean
  readonly reducedMotion: boolean
}

interface RenderedPresentation {
  readonly axes: Readonly<Record<PresentationAxis, RuntimeAxisPresentation>>
  readonly overall: AxisStatus
  readonly containerWidth: number
  readonly media: MediaState
}

function resolveRuntimeAxis(
  staticAxis: AxisPresentation,
  containerWidth: number,
  media: MediaState,
): RuntimeAxisPresentation

function aggregateStatic(axes: Readonly<Record<PresentationAxis, AxisPresentation>>): AxisStatus
function aggregateRuntime(axes: Readonly<Record<PresentationAxis, RuntimeAxisPresentation>>): AxisStatus
```

- Only exact-certified adapters reach this catalog. `hostVersion` is the exact
  adapter host version; no observed/adapter split or fallback mode is emitted.
- The 0.2.0 Client validator accepts only schemaVersion 2; it has no v1 catalog
  fallback. A mixed 0.1.9/v2 pair fails closed until reload/restart.
- `grammarHash = sha256(canonicalGrammarJSON)`; `catalogHash =
  sha256(canonical catalog payload excluding catalogHash)`.
- Cache key is `(adapterId, catalogProfile, grammarHash, catalogHash)`. There is
  no query-version cache split because there is only v2. HMR compares the same
  hashes, not raw object serialization.
- `HEAD`, error responses, `cache-control: no-store` retain the existing route
  contract; the route test that asserted “query string ignored” is replaced by
  v2 identity and single-version cache tests.
- `auditSummary` is fixed-size counts/pass flags. Full contrast/coverage/safety
  detail stays in compile artifacts and is **not** fetched at runtime; no audit
  route is added in 0.2.0. Self-check uses the summary.

```ts
interface FullAuditPayloadV2 {
  readonly schemaVersion: 2
  readonly profileId: string
  readonly sourceHash: string
  readonly liveryId: string
  readonly liveryHash: string
  readonly cssHash: string
  readonly contractHash: string
  readonly tokenHash: string
  readonly contrast: readonly ContrastEntry[]       // sorted by token/mode
  readonly tokenCoverage: TokenCoverageReport
  readonly cssSafety: CssSafetyReport
  readonly decorationAudits: readonly DecorationAudit[]
}

interface FullAuditEnvelopeV2 {
  readonly payload: FullAuditPayloadV2
  readonly auditHash: string // sha256(canonical FullAuditPayloadV2)
}

interface AuditSummary {
  readonly contrast: { pass: boolean; total: number; failed: number }
  readonly tokenCoverage: { pass: boolean; covered: number; inherited: number; missing: number }
  readonly cssSafety: {
    pass: boolean
    important: number
    hashSelectors: number
    remoteUrls: number
    fixedZIndexes: number
    unscopedTokens: number
  }
  readonly degradedAxes: number
  readonly unavailableAxes: number
  readonly auditHash: string // sha256 of the full compile audit report
}
```

All counts are `uint32`; `degradedAxes`/`unavailableAxes` are bounded by the
enumerated presentation axes. The canonical `auditSummary` JSON must be ≤512
bytes per livery. `auditHash` binds the summary to the full report and is verified
in release evidence; the full report is not packaged at runtime.

Canonical audit evidence:

- `FullAuditEnvelopeV2.payload` is a versioned JSON object with contrast entries
  sorted by `(token, mode)`, token names deduplicated by name, CSS-safety finding
  arrays sorted by `(code, selector, token)`, and no whitespace.
- `auditHash = sha256(utf8(canonical FullAuditPayloadV2))`; the envelope itself is
  never part of the hash, so there is no self-reference.
- The compiler emits the full report under `artifacts/liveries/<profile>/`;
  release evidence stores that exact file and its hash. It is not served by the
  Host and not packaged in npm.
- Critical summary fields are **recomputed from the full report** by the release
  gate:
  - `contrast.total = contrast.length`, `failed = entries with failure`,
    `pass = failed === 0`;
  - `tokenCoverage` counts unique token names, `missing = names not covered`,
    `pass = missing === 0`;
  - `cssSafety.pass = all finding counts are 0`;
  - `degradedAxes`/`unavailableAxes` count static axis statuses only; L5a runtime
    responsive degradation is not in the static summary.
- A malformed, contradictory or missing `auditSummary` makes the Client fail
  closed to stock and makes the release gate fail. A Catalog self-report is never
  trusted without the recomputation.
- A summary that claims `pass:true` while any count/finding contradicts it is a
  release blocker.
- `FullAuditEnvelopeV2.payload` includes the artifact identity above;
  `auditHash` is `sha256(canonical FullAuditPayloadV2)` including those identity
  fields and `decorationAudits`.
- The release gate unzips the final candidate, recomputes profileId/sourceHash/
  liveryId/liveryHash/cssHash/contractHash/tokenHash/auditHash from the packaged
  Catalog and full report, and requires exact equality. Evidence records the
  full report file's SHA-256 as well as the report path; the summary alone is not
  sufficient.



### HMR position

- 0.2.0 → 0.2.x same-major HMR:
  - `grammarHash` differs → `reload-required`;
  - `grammarHash` equal, `catalogHash` differs → refetch/switch Catalog;
  - both equal → reuse.
  - BootPayload carries both hashes; the Client validator enforces this.
- 0.1.9 → 0.2.0 and 0.2.0 → 0.1.9 are **not** HMR-compatible: the client must
  reload/restart after the plugin version changes.
- If an old client briefly sees a v2 catalog during a mixed HMR window, it may
  fail closed to stock until reload; this is a documented boundary, not a claimed
  working path.
- The new client is not required to accept a 0.1.9 catalog from an old host; a
  mixed running pair is unsupported.

### Boot and catalog content identity

`BootPayload` carries `grammarHash` and `catalogHash` alongside adapter identity.
A client accepts a payload only when the hashes match the served Catalog; a
same-grammar/different-catalog transition is a normal catalog refresh, not a
reload. The Host cache key includes both hashes so a manifest/parameter/renderer
change cannot reuse stale bytes. The route still uses `cache-control: no-store`;
the hash is a content identity, not an HTTP cache validator.

### Presets and rollback

- Presets keep `styleId` + wallpaper state; presentation/studio decoration are
  style properties and are derived. `PRESET_SCHEMA_VERSION` remains 1.
- 0.1.9's `createdWith` check validates only the producer/version **format**, not
  the version number. A 0.2.0 preset with a shared style ID and v1 fields can
  therefore be imported by 0.1.9 and is applied with the old style definition.
- An unknown style ID is rejected as `unknown-style`, not silently mapped to
  stock. All 28 existing IDs remain in 0.2.0, so normal palettes are shared.
- Rollback: record/export the current preset, restore stock, then install 0.1.9.
  The active style is reset to stock by `restoreStock()`; wallpaper local state,
  preset files and shared style IDs remain. Re-apply a shared style ID after
  rollback if desired. Presentation/Studio Decoration are ignored by 0.1.9; no
  user wallpaper/preset data is deleted. Unknown future IDs are rejected.

### AxisPresentation

Every axis has its own state; a single style-level label is only an aggregate:

```ts
type PresentationAxis =
  | 'palette' | 'typography' | 'geometry' | 'border' | 'elevation'
  | 'material' | 'chrome' | 'texture' | 'studioDecoration'
  | 'density' | 'transcriptWidth'
  | 'navigationStructure' | 'messageFlow' | 'messageUser' | 'messageAssistant'
  | 'ornament' | 'motion'

type AxisStatus = 'Full' | 'Inherited' | 'Degraded' | 'Unavailable'

interface AxisPresentation {
  readonly declared: RecipeRef
  readonly effective: RecipeRef
  readonly status: AxisStatus
  readonly missingCapabilities: readonly CapabilityId[]
  readonly fallbackReason?: string
}
```

Definitions:

| Status | Meaning |
|---|---|
| `Full` | every requested recipe is effective |
| `Inherited` | manifest explicitly asks for `host`/`stock`/`none` |
| `Degraded` | a deeper recipe was requested and a declared fallback was used |
| `Unavailable` | a required base capability is missing; style falls back to stock |

Field → layer → capability → renderer mapping:

| Manifest field | Axis | Layer | Capability | Fallback |
|---|---|---|---|---|
| `palette` seeds | palette | L1 | `theme-css` | stock |
| `typography` | typography | L2 | `host-font-family`, `font-role-hooks` | host |
| `presentation.geometry` | geometry | L3 | token-only | style base |
| `presentation.border` | border | L3 | token-only | style base |
| `presentation.elevation` | elevation | L3 | token-only | style base |
| `presentation.material` | material | L3 | `surface-material` | solid |
| `presentation.chrome` | chrome | L4 | consumed component fills | plain |
| `presentation.density` | density | L7 | `host-density-tokens` | host |
| `presentation.transcriptWidth` | transcriptWidth | L7 | `host-transcript-width` | host |
| `presentation.texture` | texture | L5b | `shell.decoration` | none |
| `presentation.studioDecoration` | studioDecoration | L5a | none (host-independent) | responsive reduce |
| `presentation.navigation.structure` | navigationStructure | L7 | `host-navigation-structure` | host |
| `presentation.messages.flow` | messageFlow | L7 | `host-message-flow` | stock |
| `presentation.messages.user` | messageUser | L6 | `message-user-role` | stock |
| `presentation.messages.assistant` | messageAssistant | L6 | `message-assistant-role` | stock |
| `presentation.ornament` | ornament | L5b | `shell.decoration` | none |
| `presentation.motion` | motion | L2/L3 | `reduced-motion` | static |

There is **no** separate `navigation.appearance` field in 0.2.0. Rail/sidebar
appearance is owned by `chrome`; adding a second field would create ambiguous
ownership until a host visual-role API exists. `navigation` therefore carries only
`structure` in v2.

Overall status priority: `Unavailable` > `Degraded` > `Full` > `Inherited`.
Gallery and Self-check show per-axis status; the aggregate is only a filter/summary.
A manifest declaring `navigation.structure: host` and `messages.flow: stock` is
Inherited, not Degraded.

`studioDecoration` is a non-host axis. The **Catalog** stores the declared
recipe and the `ResponsivePolicy`; it does not store a single responsive
effective recipe, because one Catalog serves multiple container widths. The
Client computes `RenderedPresentation` at runtime; a container-width reduction
is `Degraded` with `reason=container-too-narrow` (not a host capability miss).
It never becomes `Degraded` because a host lacks a shell slot.

Merge rules are frozen:

- Catalog stores only static `AxisPresentation`; runtime never writes back to
  Catalog or `auditSummary`.
- `resolveRuntimeAxis` starts from the static axis. Only L5a
  `studioDecoration` can change due to container width: >999 Full, 799<w<=999
  Degraded (reduced), 599<w<=799 Degraded (minimal), w<=599 Degraded (none).
  `Unavailable` static axes remain Unavailable; other axes copy the static value.
- `effective` is always a concrete `RecipeRef`; an Unavailable axis uses its
  declared fallback (`stock`, `host`, or `none`) rather than `undefined`.
- `aggregateStatic` and `aggregateRuntime` both use priority
  `Unavailable > Degraded > Full > Inherited`.
- Gallery uses runtime overall for the live panel and static overall for Catalog
  previews; Self-check shows both labels when they differ. `auditSummary` counts
  static axes only, so runtime responsive degradation is visible in the live UI
  but never corrupts the immutable audit evidence.

Static/runtime truth table:

| Condition | Status | Effective / reason |
|---|---|---|
| required base `theme-css` missing | style Unavailable | all axes fall back to stock; overall Unavailable |
| required base `host-font-family` missing | typography Degraded | host font; style remains available |
| required recipe capability missing, declared fallback succeeds | Degraded | fallback recipe; `missingCapabilities` records the missing required id |
| required recipe capability missing, fallback fails or cycles | Unavailable | declared terminal fallback; reason `fallback-failed`/`fallback-cycle` |
| optional capability missing | unchanged (Full or Inherited) | missing id recorded, no status downgrade |
| explicit `host`/`stock`/`none` | Inherited | declared value; `missingCapabilities` empty |
| container width reduction (L5a only) | Degraded | reduced/minimal/none; reason `container-too-narrow` |
| `forced-colors` | decorative axes (texture/ornament/studioDecoration) hide | effective none; reason `forced-colors`; do not mark style Unavailable |
| `reduced-transparency` | material glass→solid | material Degraded; reason `reduced-transparency` |
| `reduced-motion` | non-static motion→static | motion Degraded; reason `reduced-motion` |
| multiple media flags | all applicable rules apply | forced-colors decoration hide wins for decoration axes; transparency/motion are orthogonal |
| `Unavailable` on a non-base axis | axis Unavailable | only that axis uses its terminal fallback; style stays available |
| `Unavailable` on `theme-css`/palette | style Unavailable | whole style falls back to stock |

`missingCapabilities` is always the sorted unique set of unavailable required ids
for Degraded/Unavailable axes; optional ids are listed separately in the
compiler report but never change status. `fallbackReason` is never inferred from
DOM state.

## Client API identity

The frozen `ClientApiContract` must cover every slot the Client actually consumes,
not only `settingsSection`:

- `main`
- `sidebar.panellist`
- `settings.section`

For each slot the hash payload must include:

- key and scope;
- owner props shape/shape hash;
- `register` and `inject` semantics/version;
- lifecycle/disposal contract;
- required services/locale/theme hooks used by the slot.

If any consumed slot is absent from the snapshot, profile reuse/override fails
closed. A changed slot key, owner props, scope, register/inject semantics or
service dependency must change `clientApiHash`; otherwise a green hash is not
evidence of compatibility. L5b `shell.decoration` is added to this list only after
its structured contract exists.

## Catalog profile identity

The current `catalogProfileId` hashes token contract plus boolean capabilities; it
is insufficient for v2. The 0.2.0 hash includes:

- full grammar object (catalog/presentation/decoration/preview/parameterSchema);
- compiler version;
- declared capability vector (exact adapter only);
- slot/visual-role/stacking contract hashes **only when those structured

### Catalog profile override v2

Override entries must be structured and verifiable:

```ts
type GrammarIdentity = LiveryCatalogV2['grammar']
// Available capabilities from the exact contract, sorted unique; not the declared list.
type CapabilityVector = readonly CapabilityId[]

interface ProfileIdentity {
  readonly profileIdentityVersion: 2
  readonly hostVersion: string
  readonly loaderAbiHash: string
  readonly hostApiHash: string
  readonly clientApiHash: string
  readonly tokenHash: string
  readonly layoutHash: string
  readonly compilerVersion: string
  readonly grammar: GrammarIdentity
  readonly capabilityVector: CapabilityVector
  readonly clientSlotHash: string
  readonly catalogProfile: string
}

interface ProfileCompatibilityDiff {
  readonly tokenChanges: readonly {
    readonly kind: 'additive' | 'renamed' | 'value-only' | 'removed'
    readonly name: string
    readonly from?: string
    readonly to?: string
  }[]
  readonly layoutChanges: readonly {
    readonly kind: 'additive' | 'renamed' | 'value-only' | 'removed'
    readonly name: string
    readonly from?: string
    readonly to?: string
  }[]
  readonly addedCapabilities: readonly CapabilityId[]
  readonly removedCapabilities: readonly CapabilityId[]
  readonly diffHash: string
}

interface CatalogProfileOverrideDocumentV2 {
  readonly schemaVersion: 2
  readonly overrides: readonly CatalogProfileOverrideV2[]
}

interface CatalogProfileOverrideV2 {
  readonly schemaVersion: 2
  readonly target: ProfileIdentity
  readonly provider: ProfileIdentity
  readonly effectiveCatalogProfile: string
  readonly compatibility: ProfileCompatibilityDiff
  readonly reviewedReason: string
}
```

Validation rules:

- loader/host/client API hashes must be equal between target and provider;
- token/layout hashes may differ only when a structured
  `ProfileCompatibilityDiff` proves additive/renamed/value-only changes and the
  compiler gate accepts the diff; they are not required to be equal;
- full `grammar` objects must be byte-equal after canonical JSON; profileIdentityVersion must be 2;
- `clientSlotHash` must be recomputed from the structured Client slot contract;
- capabilityVector must be recomputed from the exact adapter and recipe/base-axis derivation;
- the provider catalog profile is recomputed from provider facts and must equal
  `provider.catalogProfile`; a hand-written value is not trusted;
- target/provider token/layout differences that change rendered bytes are
  rejected, not hidden behind a reason;
- the reader enforces `schemaVersion === 2`, rejects duplicate host entries,
  unknown hosts, unknown recipe/grammar IDs, and any field it cannot recompute;
- legacy v1 override files are rejected, not ignored; a migration requires a new
  reviewed v2 file with recomputed hashes;
- target and provider identities are recomputed from their snapshots, never
  copied from the JSON;
- the existing rc.1/rc.2 shared-profile case remains legal (API hashes equal,
  token/layout differ, structured diff accepted); the override reader must not
  require token/layout equality.

Document semantics:

- `target.catalogProfile` is the **intrinsic** profile computed from target facts
  before any override.
- `provider.catalogProfile` is the provider's compiled profile.
- `effectiveCatalogProfile` is the profile the target actually serves; it must
  equal `provider.catalogProfile` and the recomputed provider profile.
- `diffHash = sha256(canonical compatibility diff)`; the diff may contain additive,
  renamed, value-only and removed entries simultaneously. Removed token/layout
  facts require a render-byte check, not a prose reason.
- Duplicate `target.hostVersion` entries, unknown hosts, missing fields and
  uncomputable diffs are document-level errors; the reader rejects the whole
  document, not just one entry.

Current `ClientApiContract.slots` has only settings/locale; the extractor cannot
produce slot/role/stacking hashes. Therefore:

- L5b is disabled and no slot hash is claimed in 0.2.0;
- until `main`, `sidebar.panellist` and `settings.section` are all hashed, all
  profile overrides are disabled (exact profiles only);
- an override that requires unavailable hash fields fails closed;
- overrides validate structured fields, never a free-text reason;
- once upstream adds structured slot/role/stacking data, add it to the snapshot
  and profile identity before enabling L5b.

## Exact-certified depth

- 0.2.0 accepts **exact-certified adapters only**; unknown 0.2.x hosts fail
  closed as a whole.
- This protects L1–L4 too: loader, route, client service and lifecycle APIs are
  not proven by a version string. Masking L5b–L7 would not make L1–L4 safe.
- Compatibility fallback returns only after a trusted runtime contract
  fingerprint can match loader/host/client API hashes; a version-only fallback
  is not acceptable.
- The current boot path must be narrowed before 0.2.0 ships.

## L5a / L5b decoration

### L5a — Studio Decoration

- Manifest field: `presentation.studioDecoration` (recipe ID + bounded params).
- Used by Livery-owned gallery/wallpaper/settings pages only.
- Does not use host capability, `presentation.ornament`, Host Preview or catalog
  effective host axes.
- Renderers are Client built-ins; geometry is deduplicated by recipe.
- Still bound by a11y, primitive and performance budgets.

Responsive invariants, by actual panel container width (not viewport alone):

- `width > 999`: full decoration, safe inset 16px, no clipping.
- `799 < width <= 999`: reduce to corner/rail primitives; hide wide ornamental
  fields.
- `599 < width <= 799`: reduce to one frame/one accent primitive; no
  text-adjacent ornament.
- `width <= 599`: `studioDecoration: none`; keep palette/typography.
- These are **continuous** intervals; fractional widths use the same `<=`/`>`
  comparisons (e.g. 999.5 is full because it is >999; 799.5 is reduced;
  599.5 is minimal).
- All L5a pages use one authoritative container: the Livery workspace scroll
  container `[data-testid="livery-panel"] .livery-panel__body`, with
  `container-name: livery-studio`, exactly one per page. Gallery, wallpaper and
  settings must not nest a second same-name container. Existing wallpaper 959/639
  and workbench 1100 layout breakpoints remain layout breakpoints, not parallel
  decoration protocols; L5a does not fork them.
- 200% zoom follows the same container rules; no overflow, no clipped focus.
- All decorative nodes are `aria-hidden`, non-focusable, pointer-events none.
- `forced-colors` hides; reduced transparency removes blur; reduced motion is
  static.
- Acceptance measures the actual L5a container width at
  `1000, 999.5, 999, 799.5, 799, 599.5, 599`; viewport width alone is not
  enough.

### L5b — Shell Decoration (deferred)

The target API is a dedicated **`shell.decoration`**, not the generic
`shell.overlay`. Current `shell.overlay` is above the columns and explicitly can
hold toast/status; it has no guarantee below Modal/Toast/Tooltip. Using it for
ornament would be unsafe.

L5b requires a frozen `shell.decoration` slot with:

- owner props and scope;
- lifecycle (mount, replace, dispose);
- formal stacking below Modal/Toast/Tooltip/Menu/HoverCard;
- `ctx.effect` registration/disposal;
- one overlay per page;
- click-through and zero accessibility-tree presence;
- HMR replace/reuse without duplicates;
- atomic preview/cancel/apply/restore-stock;
- uninstall zero residue.

Current contract has no such slot. L5b therefore ships nothing in 0.2.0; all hosts
report `ornament: none` and zero overlay nodes.

### Decoration data model

- Client built-in renderers; manifest/catalog only recipe IDs and bounded
  parameters.
- Primitive allowlist is a discriminated union, not a string:

```ts
type DecorationPrimitive =
  | { kind: 'line'; x1: number; y1: number; x2: number; y2: number; stroke: TokenRef; width: number }
  | { kind: 'rect'; x: number; y: number; w: number; h: number; fill?: TokenRef; stroke?: TokenRef; width?: number }
  | { kind: 'circle'; cx: number; cy: number; r: number; fill?: TokenRef; stroke?: TokenRef; width?: number }
  | { kind: 'polyline'; points: readonly [number, number][]; stroke: TokenRef; width: number }
  | { kind: 'path'; pathId: PathId; x: number; y: number; scale: number; fill?: TokenRef; stroke?: TokenRef; width?: number }
```

- Coordinates use a frozen `viewBox="0 0 1000 1000"`; all numbers must be finite
  and within `[0,1000]` — out-of-range input is rejected, never silently clamped.
  Stroke width is `[0.5,8]`; radius is `[1,500]`.
- `polyline` has 2–16 points; `pathId` resolves through a frozen path registry
  with `^[a-z][a-z0-9-]{0,31}$`, no arbitrary path data.
- `TokenRef` must reference a compiler-generated private decoration token; no
  raw colour, `currentColor`, URL, or host token name.
- No `foreignObject`, `filter`, `href`, event attribute or text.
- Canonical primitive serialization sorts keys, rounds to 3 decimal places with
  half-away-from-zero, normalizes `-0` to `0`, forbids exponent notation, and is
  used by `decorationAuditHash`.
- Independent `DecorationAudit` emits:

```ts
interface DecorationAudit {
  recipe: string
  recipeHash: string
  rendererVersion: number
  pathRegistryHash: string
  grammarHash: string
  primitiveCount: number
  primitiveKinds: readonly string[]
  tokenRefs: readonly string[]
  issues: readonly { code: string; path: string; message: string }[]
  decorationAuditHash: string // sha256(canonical recipe + primitives + versions)
}
```

- Audit output is verified by a dedicated gate; CSS audit is not sufficient.
- Per-recipe geometry deduped; never 28 SVG copies.
- At most 16 primitives per recipe, one frame overlay per page, no unbounded
  animation, no scroll-frame updates.

## Risks

1. **Catalog size**: v2 presentation plus auditSummary may exceed cap; hard fail
   and payload trimming are required; no budget increase.
2. **L5a code size**: Studio renderer adds client bytes; dedupe and limited
   primitives; no per-style SVG.
3. **Baseline docs**: reconciled in this revision; keep the archived 0.1.x
   proposals out of current policy citations.
4. **Upstream contract**: L5b/L6/L7 remain unavailable until structured slot/role
   contracts and hashes exist.
5. **Rollback**: active style resets to stock by design; wallpaper and preset
   data remain. Document the export-first procedure before release.
